# Live 14.00 browser-process image and launcher boundary

Updated 2026-10-20. These observations come from the connected retail PS4 reporting firmware 14.00, session `70f88a40719c4399a366ad3e30265d84`. They identify code and startup dependencies in the current browser process. They do **not** establish a sandbox escape, kernel access, or the exact identity of the much larger mapped WebKit module.

The raw RX image is exactly 32,768 bytes with SHA-256 `85f5f0a1810caa122be109ed513d0638646e1a69369d5ba3e899df4686453e96`. [The collector script](../tools/collect_live_self_map.py) checked offset coverage and matched the independent entry sample. One earlier 7,680-byte response exceeded the collector's output limit and produced a `probe_error`; the page kept polling. It was replaced with smaller chunks. The first local assembly attempt rejected an empty slice at the final boundary after all device captures were complete; fixing that local condition and rerunning assembly did not require another device read.

## Static analysis and attribution limit

The low mapping's three-segment shape and its `0x4730` entry offset match the on-disk `NKWebProcess.self` header. A later same-process [module-info query](LIVE_MODULE_INVENTORY_14.md) returned `NKWebProcess.self` for handle zero, directly confirming the loaded module name. No byte-for-byte comparison with a decrypted shipped code segment is available. The [synthetic ELF](../evidence/live/rx_0x1730000_14.00.synthetic.elf) is an **analysis container assembled from live RX bytes**, not Sony's original SELF or a complete process dump. Its construction and provenance are recorded in [the builder](../tools/build_live_self_elf.py) and [metadata](../evidence/live/rx_0x1730000_14.00.synthetic.json).

Headless Ghidra analysis of this local container identified 119 functions in the captured region. [Entry analysis](../evidence/live/ghidra_entry_analysis.txt) places the entry at `0x1734730`, which reaches a startup function at `0x1733cd0`. [Selected-function decompilation](../evidence/live/ghidra_init_analysis.txt) shows fixed library/module loads, including `SYSCORE`, `NETCTL`, `SYSTEM_SERVICE`, and `NK_WEBKIT`, followed by application, network, SSL, and WebKit initialization calls. These are static-analysis interpretations of observed 14.00 bytes. The launcher code examined so far has no demonstrated browser-controlled escape path.

REA accepted the raw image but its available Windows provider did not support raw x86-64 analysis; the separate Ghidra MCP had no running GUI instance. Local Ghidra headless analysis produced the above files. The software limitation is not evidence about the PS4.

## Next decision gate

The launcher and [module inventory](LIVE_MODULE_INVENTORY_14.md) give a measured 14.00 process identity and name the libraries loaded beside WebKit. The next useful test must name an interface reachable from a browser-controlled input, predict a privileged or cross-process effect, and include a matched ordinary control. The fixed startup loads alone do not meet that gate. Before claiming a sandbox escape, require an out-of-process authority change, protected-resource access, or another independent effect that cannot be explained by ordinary browser-process behavior. Preserve the current RX image as a baseline for identifying the actual 14.00 module that handles that interface.
