# Firmware 14.00 History deserialization: one-byte out-of-bounds read/write

**Further result:** [Controlled cross-allocation read/write](HISTORY_NEIGHBOR_RW_14.md) was subsequently demonstrated across eight separately cloned resizable-buffer backing stores, including a fresh-page write repeat. The initial one-byte finding below remains the minimal reproducer.

On October 19, 2026, the connected retail PS4 reported `PlayStation 4/14.00`. The operator had checked **Settings → System → System Information** and reported 14.00. A fresh, source-guided History probe constructed a `Uint8Array` with a JavaScript-visible `byteOffset` of 8 over an 8-byte resizable `ArrayBuffer`. Its serialized length was `2^64−8`; the view reported approximately `2^64` bytes in JavaScript. Indexed access at `view[0]` read numeric `0`, then a one-byte write of `0xA5` read back as `0xA5`. A normal view over that same buffer returned `undefined` at index 8. The in-bounds first and last bytes remained `0x41`, and cleanup passed. The exact read/write result repeated on a freshly connected page with the same probe source hash.

This is a **controlled one-byte out-of-bounds read and write relative to the backing buffer's eight-byte logical length** in the 14.00 browser. The tested address is one byte past that buffer. It may still lie inside allocator padding; the experiment does not locate a neighboring allocation, establish arbitrary-address access, or establish a kernel path.

## Mechanism and source status

The [pre-fix WebKit serializer and deserializer](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/bindings/js/SerializedScriptValue.cpp) choose object-reference width at pool sizes `0xff` and `0xffff`. The [upstream BigInt fix](https://github.com/WebKit/WebKit/commit/010c6bdfb0cde0485d31f0260ab9a046fa9b8567.patch) removes a BigInt value that was incorrectly added to the deserializer's object pool. With 253 graph entries, our writer has 255 objects when it emits a repeated reference, while the reader has 256. The reader consumes two reference bytes where the writer emitted one. A crafted 256-code-unit UTF-16 property name supplies the displaced byte stream. The first probe made that stream a self-reference. The view probes made it `ArrayBufferViewTag`, `Uint8ArrayTag`, offset, length, and `ObjectReferenceTag` for the chosen backing buffer.

The [deserializer's view path](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/bindings/js/SerializedScriptValue.cpp) accepts a `uint64_t` byte offset and length, then calls `Uint8Array::wrappedAs`. WebKit's [native typed-array wrapper](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/JavaScriptCore/runtime/GenericTypedArrayViewInlines.h) checks the subrange for fixed buffers but skips that check for a resizable buffer. The [JS view construction](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/JavaScriptCore/runtime/JSArrayBufferView.cpp) sets its native data pointer to `buffer.data() + byteOffset`. The [out-of-bounds test](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/JavaScriptCore/runtime/JSArrayBufferViewInlines.h) and [indexed access check](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/JavaScriptCore/runtime/JSGenericTypedArrayViewInlines.h) add offset and raw length in `size_t` without checked arithmetic. On a 64-bit engine, `8 + (2^64−8)` wraps to zero, so the view appears in bounds while its index 0 points one byte beyond the buffer.

That source chain predicts the captures. It is an inference about the PS4's implementation, because the exact running binary has not been matched to this upstream commit. The live 14.00 observations independently establish the inconsistent view metadata and one-byte access.

## Next experiments

Keep the existing one-byte read/write probe as the minimal regression. The next useful discriminator is a controlled neighboring allocation or a non-mutating layout observation that shows which allocation owns the out-of-bounds byte. Use fresh pages and retain both normal and forged-view controls. The present result already crosses the native-memory gate for the browser, but address control, repeatable access to a chosen neighboring object, and a kernel path are separate milestones.
