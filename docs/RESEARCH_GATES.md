# Research gates

These gates keep the next experiment tied to a question that an observation can answer. Browser-level observations can advance before exact binary attribution, but source-specific and kernel claims require that missing evidence.

| Gate | Required evidence | Current state |
| --- | --- | --- |
| 0. Identify environment | Console version checked in Settings; raw browser user agent and capture ID recorded | Passed for the console version: operator checked System Information and reported 14.00; capture user agent and entered label agree; running browser binary identity remains unknown |
| 1. Establish browser baseline | Small controls repeat across browser sessions, with full inputs and outputs | Passed: typed-array and MessageChannel baseline plus ordinary clone controls |
| 2. Attribute running code | Firmware-specific module bytes or source directly tied to the running browser build | Passed for the **mapped browser-process code**: the current 14.00 session supplied a named census and exact, hashed RX/RO/RW coverage for all 26 loaded SPRX modules. Shipped-file headers and unmapped sections remain unknown, as do privileged service and kernel binaries. [Full capture](FULL_SPRX_DUMP_14.md). |
| 3. Test a falsifiable browser hypothesis | Exact operation, predicted result, normal control, and a distinct failure oracle | Passed: BigInt before repeated object reference causes observable substitution; controls isolate placement |
| 4. Classify browser impact | Reproducible integrity or access difference with raw evidence and cleanup | Passed: wrong cloned-buffer reference and [canvas slot reuse](CANVAS_NATIVE_FOLLOWUP.md) with a cross-object pixel write repeated on a fresh page |
| 5. Establish a security primitive | Evidence for native memory unsafety, security-boundary crossing, or another practical impact | Passed: the forged view read and wrote separate cloned resizable and fixed buffers, with fresh-page repeats; it also read and temporarily changed a live native node-list pointer vector, then restored it. A new fresh-page repeat read and reversibly substituted an eight-byte live JSArray element word, changing object identity and restoring it. These are bounded, measured targets. |
| 5a. Calibrate absolute addressing | Two independent measurements that locate a known live allocation in the forged view's address space, repeated on a fresh 14.00 page; a reversible read/write at the calculated location | Passed for measured JavaScript objects in two fresh 14.00 sessions. An anchor's leaked word and live property index gave the same page-aligned view base; a later object's word predicted its property index without a target scan, and a view write changed/restored that property. A separate read reached two newly created function cells. [Evidence](HISTORY_ADDRESS_DIRECTED_RW_14.md). |
| 5b. Demonstrate browser execution independently | A fresh 14.00-derived target and controlled native redirection with an output that ordinary JavaScript or a data-only write cannot explain, plus restoration and a repeat | **Passed on two independent page sessions.** Current-process gadget bytes, import targets, wrapper bytes, owned chain data, and function slot were rechecked; the number-20 native call returned `140` then `141` in initially zeroed owned frames. Both probes restored the modified pointers and normal function behavior. [Current evidence](HISTORY_NATIVE_CALL_14.md). |
| 5c. Map the sandbox boundary | Byte-checked 14.00 process identity and matched allowed/denied resource observations with error and cleanup evidence | Partial: UID is `1`; `setuid(0)` and a parent-process information query returned `EPERM`, while the self query succeeded. Upstream jail and capability bits in a source-shaped self record are clear; Sony's sandbox-state wrapper returned `1`. Directory and device controls map only limited access. A live-byte-checked, read-only `sceSystemServiceGetAppStatus` call returned success and data through the LNC client, showing a reachable service interface without an unauthorized effect. [Boundary record](SANDBOX_BOUNDARY_14.md), [process model](PROCESS_BOUNDARY_MODEL_14.md), [service interface](SYSTEM_SERVICE_IMAGE_14.md). |
| 6. Establish a kernel path | Firmware-specific kernel entry point and an observation distinguishing it from ordinary behavior | Unknown |

The [History native-memory finding](HISTORY_NATIVE_OOB_14.md) is the leading browser result: it reaches a byte outside the logical backing buffer for both read and write, and repeats on a new page. The [canvas native follow-up](CANVAS_NATIVE_FOLLOWUP.md) separately found a stale wrapper changing a new context's pixel, twice on fresh pages; the [multi-stale follow-up](CANVAS_MULTI_STALE.md) added four stale wrappers addressing one context. The [TransformStream finding](TRANSFORM_STREAM_CANDIDATE.md) and [font-loading lead](FONT_FACE_LEAD.md) remain warning paths without a measured byte access. The console's 14.00 version has been reported from System Information; firmware binary identity is still unknown.

Add one diagnostic probe at a time under `probes/`, with a normal control and an outcome that distinguishes competing explanations. Keep exact source and manifest digests with the raw capture. A desktop control proves the intended ordinary behavior; it cannot identify the console's implementation.

For the current TransformStream lead, the completed three-element wrong-type iterator has been watched after passing JavaScript-only and synchronous-marker controls, and produced an immediate warning and page refresh. The earlier wrong-type attempt coincided with an unobserved cutoff and later Rest Mode; the two other observed warnings used shortened sequences that the public source's fatal bounds check can explain. Further tests need a discriminator beyond another warning. Do not promote the symptom to a usable native memory primitive without evidence of a controlled native effect.

No kernel claim can be based solely on a browser exception, a memory warning, an upstream FreeBSD implementation, or a successful syscall return. A kernel hypothesis needs a firmware-specific reason and an observation that distinguishes it from ordinary API behavior.
