# TransformStream wrong-type browser failure on the reported 14.00 browser

**Status, 2026-10-19:** On watched console runs, replacing the second item of TransformStream's three-item iteration with an ordinary object was followed immediately by **“There is not enough free system memory”** and a page refresh after the operator pressed OK. The final run saved durable markers from inside the replacement branch, at the third value, and when the iterator reported completion. The benign synchronous-marker control passed first. This is a specific browser failure matching the input class in a [WebKit type-confusion fix](https://github.com/WebKit/WebKit/commit/8fd92b1021d310b2580eb3ac7913911eb14dc476). The complete three-element sequence excludes the shortened-vector bounds check as an explanation **if the published source matches the running browser**. It does not establish that the running binary matches Sony's public source, or that memory corruption, controlled native read/write, code execution, sandbox escape, or kernel access occurred. The published cast implementation makes a null dereference plausible. The operator checked **Settings → System → System Information** and reported 14.00; the browser user agent also reports 14.00. No browser binary fingerprint has been captured.

## Why this candidate was tested

The public [Sony PS4 WebKit source page](https://www.playstation.com/en-us/oss/ps4/webkit/) labels its 616-1300 archive for system software **13.00 and later**. Its `Source/WebCore/Modules/streams/TransformStream.cpp` has this sequence at lines 114–117: convert a JavaScript result through the iteration protocol; check `results.size() == 3` only with `ASSERT`; then dereference two `jsDynamicCast` results without a null check. In a release build, `ASSERT` is normally inactive. Our extracted member's SHA-256 is `0fbdf7c4a3c0f1bbb19ccdf737f5d3746ec3b79f2adfe53772d23fd1ee33b807` ([source provenance](../references/README.md)). Sony also lists a 601-1300 archive for the same firmware range; a full ZIP member-name inventory found no `TransformStream` file there. The live API's presence therefore favors the 616 branch as the useful public analogue, but this is still source evidence, not a binary match for the console.

An [upstream WebKit fix](https://github.com/WebKit/WebKit/commit/8fd92b1021d310b2580eb3ac7913911eb14dc476) for CVE-2026-43705 replaces the assertion with a runtime size check and rejects unexpected readable/writable object types before dereference. Its commit description identifies overridden `Array.prototype[Symbol.iterator]` as the input path and describes attacker-influenced dereference, reference-count, and virtual-call effects for **wrong-type substitution**. That is distinct from the shortened-vector path's fatal bounds check. The [WebKitGTK/WPE advisory](https://www.webkitgtk.org/security/WSA-2026-0004.html) describes the flaw as type confusion that may lead to memory corruption; its affected-version statement concerns those ports, not PS4. The first live wrong-type attempt was obscured by Rest Mode; the later watched attempt produced the warning and refresh described below.

## Evidentiary limit and next gate

The first type-guard attempt has **no interpretable outcome** because the PS4 was later found in Rest Mode and there is no process telemetry or contemporaneous screen observation. The later watched wrong-type attempts have immediate warnings and page refreshes after passing controls, and the last test proves its three-item iterator completed. That rules out an intentionally shortened vector in the public-source analogue and makes this a strong browser-bug candidate matching the upstream WebKit regression's failing input class. It is **not yet a usable security primitive**: no native fault address, controlled read/write, or crossed boundary has been demonstrated. The separate structured-clone result remains the strongest demonstrated integrity defect, limited to valid cloned buffers. The [official PS4 user's guide](https://manuals.playstation.net/document/en/ps4/settings/errorhistory.html) documents Error History; absence of an entry does not alone rule out a browser failure. A fresh browser session needs its own connection and ID.

The Sony archive's `JSDOMConvertSequences.h` returns a vector of however many elements the iterator yielded; it can return a shortened vector after an early `done` or exception. `TransformStream.cpp` only uses `ASSERT(results.size() == 3)` before `results[1]` and `results[2]`. Crucially, the same archive's `Vector.h` implements `operator[]` through `at()`, which calls the default `CrashOnOverflow` handler when the index is outside `size()`. `Forward.h` sets that default, and `CheckedArithmetic.h` defines the handler as `CRASH()`. Therefore, **if these source files match the running browser**, the one-element path should terminate at a bounds check, before any out-of-bounds vector read. This gives a conservative explanation for the warning; it is not evidence of a native read/write primitive. Exact files and hashes are in [source provenance](../references/README.md).

The same archive's `JSCast.h` shows that `jsDynamicCast<JSReadableStream*>` checks the object's runtime class and returns `nullptr` when a plain object does not inherit from that class. On the public source path, the subsequent unconditional `->wrapped()` would therefore use a null result. That can explain a process failure without showing control of a native pointer. The upstream commit's broader impact description is a reason to investigate, not proof that this particular plain-object run got past the null dereference or exercised its described reference-count and virtual-call effects. We have no native fault address or heap telemetry to distinguish those possibilities on the console.

A [small isolated compiler analogy](NULL_CAST_COMPILER_ANALOGY.md) checked whether optimization alone obviously removes a failed-cast check before the unguarded member access. Clang 18.1 and GCC 14.2 at `-O2` both retained the check and then accessed a low address on the wrong-type path. This supports keeping null dereference as the conservative hypothesis, while saying nothing definitive about Sony's compiler, flags, generated wrapper layout, or running binary.

The iterator-throw probe was mistakenly treated as harmless: throwing during conversion can produce the same shortened vector. Neither it nor any wrong-type probe should be queued as a routine control. The completed wrong-type sequence now resolves the vector-length ambiguity. Further work needs a discriminator beyond another warning: a native crash signature, a controlled effect in userland memory, or an independently attributed 14.00 browser binary. None is available from the current page captures. Repeating the warning without such a measurement would not advance the security-primitive gate.

## Discriminator arm 2 result, 2026-10-19

The [discriminator probe](../probes/transform_stream_cast_discriminator_v1.js) (`source SHA-256 6658c07b4457419c70beebe37b1ff1dcda59677c4406e7addc25985e7203891f`) ran as command `006afb1a640c462795863914bece4d78` on fresh session `8145a3d7d7f84c118e2a3c3ad5889101`, claimed at `05:19:44.085266Z`. Its markers, in order: `before_constructor` at `05:19:44.137136Z`, `arm1_replaced` at `05:19:44.163017Z`, `arm1_returned` at `05:19:44.181376Z`, `arm2_replaced` at `05:19:44.198558Z`. No `arm2_threw` marker followed. The operator then reported the immediate system-memory warning; the last marker check was at 05:20:03Z, and the warning time was not recorded. The command remains `claimed`, with no result and no capture.

Arm 1 put a genuine `ReadableStream` in the readable slot and the constructor returned, as the source model predicts. Arm 2 put the number `7` there. The earlier prediction of a catchable `TypeError` was **wrong**. Reading the 616 sources changes the model:

- `Converter<IDLObject>::convert` returns an empty result for a non-object after calling `exceptionThrower`, and `DefaultExceptionThrower` throws a `TypeError` ([JSDOMConvertObject-sony-616-1300.h](../references/upstream-webkit/JSDOMConvertObject-sony-616-1300.h), [JSDOMConvertBase-sony-616-1300.h](../references/upstream-webkit/JSDOMConvertBase-sony-616-1300.h)).
- The generic sequence path appends a converted element only when no exception is pending, so the failed element is skipped ([JSDOMConvertSequences-sony-616-1300.h](../references/upstream-webkit/JSDOMConvertSequences-sony-616-1300.h), lines 52–59).
- The sequence loop stops after a callback leaves an exception pending: both the fast-array and iterator paths return without visiting later items ([IteratorOperations-sony-616-1300.h](../references/upstream-webkit/IteratorOperations-sony-616-1300.h), lines 73–79 and 95–99). For slot 1, the loop therefore ends with one element. `TransformStream.cpp` lines 114–117 do not check the pending exception, and `results[1]` on that one-element vector hits the bounds check, which calls `CrashOnOverflow` ([Vector-sony-616-1300.h](../references/upstream-webkit/Vector-sony-616-1300.h)). That is the same fatal path the public source already names for shortened sequences.

This predicts a fail-stop, not a catchable exception, for a non-object at slot 1, and it fits arm 2. The paths differ by input. A plain object or a `WritableStream` at slot 1 converts successfully, so the loop visits all three items. The readable cast then returns null, and `->wrapped()` dereferences null. That fits the earlier plain-object runs and predicts the same null path for the writable arm. An exception that stops the loop early, such as the iterator-throw probe, reaches the same unchecked indexing with a short vector. The model is still a source-based hypothesis: it assumes the running binary matches the 616 sources, and the observations do not identify the faulting address or the crash type on the console.

The writable crash arm (`transform_stream_cast_writable_arm_v1`) is still unqueued. Under the refined model it still predicts a crash, so it would only add a class-versus-object distinction at the cost of another warning. The operator paused console work on this lead on 2026-10-19, and no further probes are queued. Gate 5 remains open.
