# Firmware 14.00 History deserialization: live fixed-buffer cross-write

The forged `Uint8Array` established in [the native out-of-bounds result](HISTORY_NATIVE_OOB_14.md) can reach a **live, separately cloned fixed-length `ArrayBuffer`** on the retail PS4 reporting firmware 14.00. A 262,144-byte differential scan found the cloned buffer at forged-view index 155,640 in one run: filling its normal view changed exactly 65,536 consecutive bytes visible through the forged view. A follow-up located that same live allocation dynamically, wrote one byte through the forged view, observed the change through the fixed buffer's normal view, and restored the original byte. The input-side fixed buffer and the forged view's eight-byte resizable backing buffer were unchanged.

This crosses an allocation-class boundary: the forged view is attached to a resizable buffer, while the affected allocation is a fixed buffer cloned by History. The two allocation classes have different paths in [WebKit's `ArrayBuffer` implementation](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/JavaScriptCore/runtime/ArrayBuffer.cpp). The console measurements establish the live alias independently of that source interpretation. **Arbitrary process read/write and WebKit code execution remain unproven.**

All three captures passed `python -m fw14lab.verify`. The console's user agent reports `PlayStation 4/14.00`, and the operator checked System Information. The exact running browser binary has not been recovered. The different measured positions across the write runs are why the probe locates the live buffer by a full-region differential comparison; sampling only at 64 KiB strides missed the alias. The local, Git-ignored [evidence snapshot](../evidence/2026-10-19-history-fixed-rw.zip) contains 136 raw captures, 256 exact probe snapshots, and a consistent SQLite backup; ZIP SHA-256 `722360139c525a675445b09a3400fa7a471d803eabe13b1a39a102241b8811ce`.

Controls and rejected interpretations matter here. The earlier fixed-buffer marker at a stride address stayed unchanged when either the input-side or cloned fixed buffer was filled in [`d0b2d67efc7d4d53803bae38a7b33253`](../captures/d0b2d67efc7d4d53803bae38a7b33253.json), SHA-256 `adfd8f9fe677fba5aa7a022321bbd7c6bb976831bb6a2a5ef9af3a792ff9974c`. Mutating that marker did not change a subsequently deserialized History value in [`0be6bfb1462a41ddac49ed3bfd5b392b`](../captures/0be6bfb1462a41ddac49ed3bfd5b392b.json), SHA-256 `72998193d803e104f4f194e4dc0ed340662cce22dde45a570020594ebc171905`. The source of that stale marker is still unknown. A negative-offset view was visible as out of bounds and supplied no indexed access in [`1a5106527d32428fb1d983b2074383d8`](../captures/1a5106527d32428fb1d983b2074383d8.json). Transferring the forged view's own backing buffer detached it cleanly in [`9e943a9668de4c9a959fa88062d2a2d1`](../captures/9e943a9668de4c9a959fa88062d2a2d1.json). These do not supply a separate execution route.

Transferring the cloned fixed buffer to another `ArrayBuffer` kept its backing memory at the same measured address: writing the new owner's first byte changed the forged-view byte, and restoration matched in [`3ad0af01b4a24449bb17d79276d5a942`](../captures/3ad0af01b4a24449bb17d79276d5a942.json), SHA-256 `8a1bccc75fe830c69c08f0fd347c085befe411def79453471272e4746b4a2a86`. This shows that ownership transfer alone does not invalidate the forged view's access to the separate allocation.

The next gate is a source-guided attempt to access memory that carries a native pointer or control-flow value. A fixed buffer contains attacker-controlled bytes, so cross-writing that buffer alone does not imply code execution.
