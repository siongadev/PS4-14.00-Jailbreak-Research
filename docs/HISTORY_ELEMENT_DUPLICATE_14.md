# Same-type Element release branch for PS4 14.00

**Status: prepared, never run on the console.** This branch uses only the live two-slot pointer relationship measured in the current project's 14.00 captures. It does not import an offset, gadget, object layout, or source file from the old project.

The [two-slot capture](HISTORY_NATIVE_POINTER_RW_14.md) showed that a forged view can replace the first pointer in a retained 8,191-element `querySelectorAll("span")` result with its second pointer, making `item(0) === item(1)`, then restore it. In the reviewed WebKit revision, [`StaticElementList` stores `Vector<Ref<Element>>`](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/dom/StaticNodeList.h), and [`Ref` destruction calls `deref()`](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WTF/wtf/Ref.h). Duplicating an entry without adding a native reference predicts one extra dereference of the second span when the list is destroyed. The PS4 binary has not been matched to this source; the device result must decide whether the prediction applies.

In all five saved `clone_history_two_slot_hold_v2` captures, across two page sessions, the first four retained span pointers were adjacent at `0x70` spacing, and the first entry matched the temporary vector's second word. This supports using the already validated first-to-second swap as the entry gate; it does not identify a heap base or prove an allocator policy.

Use a fresh connected page for each arm. For each arm, first run `clone_history_two_slot_hold_v2` and require both measured slots, a live first-to-second swap, and successful restoration. The release probes both label the second span `fw14-element-probe` and detach it from its parent before dropping the list.

1. **Unchanged control:** run `clone_history_element_release_control_v1`, then `clone_history_element_release_gc_only_v1`. Proceed to `clone_history_element_stale_read_v1` only if the list was finalized and its weak reference is dead. The detached span should retain its label, node type 1, and `SPAN` name.
2. **Duplicate-pointer arm on a new page:** run `clone_history_element_release_mutated_v1`. It verifies that the first slot still contains the measured pointer, reads the second slot's bytes, substitutes them for the first, and requires both list entries to return the exact second span. It leaves the duplicate in place when releasing the list. Run `clone_history_element_release_gc_only_v1` next, without touching the second span. Only after confirmed list finalization run `clone_history_element_stale_read_v1` while the operator watches for a warning or refresh.

The control and modified arms differ in whether the first list pointer was replaced. A changed label or abnormal read limited to the modified arm would be a native-lifetime lead. A warning without a saved result needs the durable markers and the operator's on-screen report. Neither arm alone proves a freed allocation, reused slot, arbitrary-address access, or code execution. If a repeatable changed label appears, a separately gated same-type span reuse and reversible live-alias write would be the next evidence gate.

A local mock test verified the control preserves the first pointer and the modified arm substitutes the live second pointer; that test cannot establish console behavior.
