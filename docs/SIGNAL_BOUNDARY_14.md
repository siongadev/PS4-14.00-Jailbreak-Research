# 14.00 process-signal boundary

Updated 2026-10-20. The [FreeBSD capability-mode advisory](https://www.freebsd.org/security/advisories/FreeBSD-SA-26:28.capsicum.asc) identifies a `sigqueue(2)` path that omitted a capability-mode target restriction upstream. This is a **hypothesis generator only**: Sony 14.00 kernel equivalence and whether this browser uses Capsicum are unknown. The [FreeBSD 9 syscall list](https://raw.githubusercontent.com/freebsd/freebsd-src/stable/9/sys/sys/syscall.h) maps `kill`, `getppid`, and `sigqueue` to numbers 37, 39, and 456; all three numbers were present in our live [14.00 wrapper census](../captures/0d7687b41f104aada204059eb3ef9c64.json). The new [guarded caller installation](../captures/60e54aeccf554408b8fe908683531772.json) checked those live wrapper bytes and four benign `getpid` returns before exposing the calls. Its [errno-capable successor](../captures/31625a86172a4dddb58f8ef177cb8af5.json) also checked the current `__error` bytes and restored the page carrier. [Pinned sources](../probes/clone_history_native_invoke_install_v6.js).

The [upstream `sigqueue` implementation](https://raw.githubusercontent.com/freebsd/freebsd-src/stable/9/sys/kern/kern_sig.c) treats signal number `0` as a permission check without delivery; Sony 14.00 semantics were measured below. The probe called `getpid` and `getppid`, then compared `kill(pid, 0)` with `sigqueue(pid, 0, 0)` for **only** those two PIDs. It did not send a nonzero signal. The [first capture](../captures/01b112a88aa94eb5851cd8ea309556dc.json) returned the same pattern; the [errno capture](../captures/5b42aa15e4a84a0c83328a48833febd3.json) and [exact-source repeat](../captures/59276b88e84c4d81a0f03a2c0ca56f83.json) both measured:

| Target | `kill(..., 0)` | `sigqueue(..., 0)` |
| --- | --- | --- |
| Browser PID `145` | `0` | `0` |
| Parent PID `38` | `-1`, errno `1` (`EPERM`) | `-1`, errno `1` (`EPERM`) |

Both error captures reported valid return-word shapes and restored the page carrier. The same-source probe SHA-256 was `9fad2c629858641444826b908715609b08f3899bb58417466a61c3676130da8d`. This establishes that the parent target is denied equally by the two interfaces in the observed browser context. It does **not** show whether the browser is in capability mode, whether a different process with matching Unix credentials would be treated differently, or whether Sony's implementation contains the upstream defect. Without a known safe, independently observable same-user target, a nonzero signal or broad PID scan would not answer the escape question. This lead is paused.
