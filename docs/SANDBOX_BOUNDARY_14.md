# PS4 14.00 browser sandbox boundary

Updated 2026-10-20. The [History native-call result](HISTORY_NATIVE_CALL_14.md) gives the research page a reversible call through mapped native browser code. It does not change the browser process's credentials or the kernel's memory. This file tracks evidence needed to distinguish ordinary calls from a sandbox escape.

The old project's 14.00 wrapper census lacked ordinary stubs for the upstream System V semaphore numbers `221` and `222`, and its earlier direct-tail calibration interrupted before a semaphore call. There is no return capture or restoration proof for that command, and its marker does not establish that the syscall instruction ran. No semaphore syscall was attempted. The direct-tail route remains gated until a new execution mechanism explains this repeatable interruption; merely changing the requested syscall number would not answer it.

The [current 14.00 wrapper census](SANDBOX_WRAPPER_CENSUS_14.md) now independently captured all **293 unique stubs** in the same three 4 KiB pages: 115/117/61, with no `221`, `222`, or `510`. The exact 14.00 kernel implementation is not inspected, but a mismatched-number interior call is now a measured dead end. No System V semaphore call ran.

## Candidate selection

**New 14.00 process-record discriminator:** a byte-checked number-202 size query succeeded for the browser's own PID `145` but returned `EPERM` for its parent PID `38`, twice with identical source; an absent PID returned `ESRCH`. Two guarded self-record reads produced a 1,096-byte FreeBSD-shaped `SceNKWebProcess` record whose PID, parent PID, UID `1`, and thread count align. Under the [upstream FreeBSD 9 layout](https://raw.githubusercontent.com/freebsd/freebsd-src/stable/9/sys/sys/user.h), the capability-mode bit and `P_JAILED` bit are clear. This is a 14.00 observation with a source-derived interpretation, not proof that Sony kept the upstream flag meanings. In particular, upstream `ki_jid` can be zero even when the caller is jailed. [Exact captures, decoder, and limits](PROCESS_BOUNDARY_MODEL_14.md). This lowers the priority of advisory paths that require an actual FreeBSD jail or Capsicum capability mode and favors direct study of Sony's process confinement and its reachable interfaces.

The old project's read-only 14.00 audit (local prior-work archive: `old-webkit-project/KERNEL_PATH_AUDIT.md`, not included here) recorded ordinary socket, event-queue, AIO, and `sysctl` calls from the browser. Its 14.00 runs did not demonstrate a kernel-memory effect, a credential change, or a sandbox escape. The most developed AIO timing run observed an effective deletion before the worker's held marker; the 2,560 tagged IPv6 option readbacks found no cross-socket alias in the tested setup. The System V availability call never reached its target after direct-call calibration interrupted. The new same-page comparison explains why simply entering another wrapper's syscall suffix with RAX set to `221` is not a valid availability test. These results prevent treating any of those interfaces as an already working escape.

An [upstream FreeBSD race fix](https://github.com/freebsd/freebsd-src/commit/8f3227f527567aef53da845ab78da8e16d9051c1) concerns fd-backed event registration overlapping descriptor close/reuse. It gives a specific event-queue hypothesis, but the 14.00 browser kernel has not been identified as that upstream code. The old project's actual 14.00 registration-versus-close/reuse run showed no stale event and did not prove overlap inside the narrow kernel window; its `dup2` controls returned `EPERM`. Current-project 14.00 socket readiness, alias-close, and numeric-fd-reuse controls now [establish a source-specific event oracle](SANDBOX_WORKER_PATH_14.md): close removes the watched descriptor's event even while a duplicate retains the old socket, and a replacement at the same numeric fd produces no event until separately registered. The next event-queue experiment still needs a result that separates the race from this normal descriptor removal; another plain registration or warning would add little.

The [FreeBSD stable/9 implementation](https://raw.githubusercontent.com/freebsd/freebsd-src/stable/9/sys/kern/kern_event.c) makes the candidate more specific without establishing Sony's kernel behavior. In `kqueue_register`, an fd-backed event first obtains a referenced `fp` with `fget`, then takes the queue lock; for an ordinary socket it does not take the special file-descriptor lock reserved there for `DTYPE_KQUEUE`. With no existing note, it assigns that earlier `fp` to a new note. `knote_fdclose` holds the file-descriptor lock and removes notes already present on the queue. The [2026 upstream fix](https://github.com/freebsd/freebsd-src/commit/8f3227f527567aef53da845ab78da8e16d9051c1) specifically adds a post-lock check that the fd still names the referenced file. **Inference:** if Sony 14.00 retained the old ordering and lacks the new check, close between `fget` and queue locking could leave a note whose numeric fd and referenced file disagree. This remains a source hypothesis: no Sony kernel instructions for either function have been read, and the older 14.00 worker run did not establish that the two calls overlapped inside that interval.

A discriminating 14.00 test would retain the old socket through a duplicate descriptor, so its writer can still signal after closing the watched number, and compare against a replacement socket at the reused number. A stale old-source event after the watched number closes would differ from the established sequential close control; no event from either writer is the prior inconclusive result. The experiment needs a way to establish or greatly increase the `fget`-to-queue-lock overlap, plus bounded cleanup and a fresh-page control. Since the kernel interval is not externally observable and the earlier worker message ordering did not prove overlap, an unchanged race replay is not yet a useful live test.

The current project then validated a worker wait-to-register continuation and ran nine native-chain close/reuse comparisons with exact numeric reuse and cleanup. Three produced replacement-only readiness and six no event. In the last four, same-worker error readback separated successful registration (`0`) from `EBADF` (`9`); no run produced an old-source event or observed the internal kernel overlap. [Exact captures and limits](FD_REGISTRATION_RACE_14.md). Changing the number of intervening page-side `getpid` calls did not reliably select an ordering, so this scheduling variant is paused.

The current project has now rebuilt a [worker-side native-call path](SANDBOX_WORKER_PATH_14.md) from live 14.00 addresses. A worker returned PID `145` through the byte-checked number-20 wrapper, then repeated the call with a second, non-overlapping set of owned call buffers. A separate worker native sleep returned after 300 ms while the page's timer ran during that interval. **Two timestamped runs then placed a page-side `getpid` native call 52–53 ms into the worker's native sleep;** both returned PID `145` and sleep result zero, with both plans restored. The new project then completed a guarded user-event add/trigger/read/delete/close and **twice** woke the worker's number-363 native wait with one matching event, intact output guards, and descriptor cleanup. It also completed the three sequential socket controls above. This establishes the concurrent event interface and a source-specific readback. The current LAN HTTP page reports `isSecureContext=false` and has no `SharedArrayBuffer`; isolation headers alone cannot provide a shared atomic barrier. [The decision plan](FD_REGISTRATION_RACE_14.md) prioritizes a native wait-then-register continuation and records the remaining outcome gates. Neither the descriptor race nor a sandbox crossing has been observed.

A separate source-backed boundary candidate is [FreeBSD-SA-26:25.thr](https://www.freebsd.org/security/advisories/FreeBSD-SA-26:25.thr.asc). The [older FreeBSD 9 implementation](https://raw.githubusercontent.com/freebsd/freebsd-src/stable/9/sys/kern/kern_thr.c) also computes `p_cansignal` but omits the rejection in the targeted-thread branch of `thr_kill2`; the all-thread branch does reject. The current 14.00 wrapper census contains number `481`, which [FreeBSD 9 calls `thr_kill2`](https://raw.githubusercontent.com/freebsd/freebsd-src/stable/9/sys/sys/syscall.h). An initial invalid-TID and signal-zero control returned `ESRCH`: [capture](../captures/d030416f87b245fa9bf4e46e39292581.json). A subsequent current-page scan located a parent-process TID and repeated the targeted call twice with signal zero. Both calls returned `EPERM`, while a wrong-TID parent control returned `ESRCH` and an own-TID control succeeded: [exact 14.00 record](THR_SIGNAL_ZERO_14.md). This tests the permission boundary for that parent target without delivering a signal. It establishes no bypass for this shape and does not prove that every target or nonzero signal follows the same path.

The old project's actual 14.00 multicast source-order capture (local prior-work archive: `old-webkit-project/FW14_MULTICAST_SOURCE_COMPARISON.md`, not included here) returned `EADDRNOTAVAIL` for a valid one-source filter with no joined group, then `EFAULT` for the same request with a null source pointer. That means the Sony path accessed the source pointer before rejecting the absent membership. This is consistent with the [FreeBSD stable/14 fix](https://github.com/freebsd/freebsd-src/commit/522182827ea173e07668b1ac40a8173c620bb99e), which copies the source before looking up the filter, so the advisory's specific post-lookup stale-pointer race is a poor primary target on 14.00. The result does not prove full Sony source equivalence. The older 14.00 sequential 31/32 membership and filter tests were normal and did not expose a lifetime anomaly. A further race run needs a different firmware-specific discriminator.

The [2026 FreeBSD descriptor-poll advisory](https://lists.freebsd.org/archives/freebsd-security/2026-May/000453.html) is lower priority here. Its [procdesc fix and regression test](https://lists.freebsd.org/archives/dev-commits-src-all/2026-May/073456.html) require a process descriptor created by `pdfork`; [FreeBSD 9 assigns that entry number 518](https://github.com/freebsd/freebsd-src/blob/stable/9/sys/sys/syscall.h). Number `518` is absent in our bounded three-page 14.00 browser wrapper inventory, and the observed `/dev` listing contained no netmap node. These observations do not prove the Sony kernel lacks either feature, but they fail the browser-reachability gate for this advisory. Testing `poll` on an ordinary socket would not exercise its documented procdesc failure path.

The separately measured `sigqueue` number-456 interface did not change the observed process boundary. A [signal-zero comparison](SIGNAL_BOUNDARY_14.md) and same-source error-code repeat allowed both `kill` and `sigqueue` for the browser's own PID `145`, while both denied parent PID `38` with `EPERM`. The [upstream Capsicum advisory](https://www.freebsd.org/security/advisories/FreeBSD-SA-26:28.capsicum.asc) has a different prerequisite: a capability-mode process addressing another target it can signal under normal Unix permissions. This run did not establish that prerequisite or a cross-process effect; no nonzero signal was sent.

The [upstream UMTX shared-memory advisory](https://www.freebsd.org/security/advisories/FreeBSD-SA-24:14.umtx.asc) was screened against the live number-454 wrapper. Ordinary mutex operations `4` and `5` each wrote the same nonzero owner word into an owned buffer; operation `6` released it, clearing the word. A harmless wake also succeeded. Yet read-only operation-25 `ALIVE` and `LOOKUP` checks returned the same `EINVAL` as an invalid-operation control. `ALIVE` still returned `EINVAL` for a verified live RX mapping and for an owned address placed in the first argument, fourth argument, or both. [Raw 14.00 comparisons and limits](UMTX_SHM_GATE_14.md). Sony may omit this newer operation or reject those inputs for another reason; neither its shared-memory branch nor the advisory's destroy race has been established on 14.00. The mutex owner writeback is ordinary current-process synchronization, not a sandbox boundary change.

The next useful test must choose one reachable 14.00 interface and measure a security boundary, not merely a successful syscall. A candidate advances only with: (1) live 14.00 wrapper or entry bytes, (2) an ordinary control on owned objects, (3) a bounded outcome that distinguishes denial from permitted behavior, and (4) an independent readback of changed authority or an out-of-process/kernel effect. A kernel pointer-shaped value, error code, crash warning, or userland write alone is insufficient. The ordinary number-92 commands returned `EINVAL` on two descriptor types, and the wrapper-number mismatch produced the warning in a controlled comparison, so neither currently opens the semaphore or descriptor-replacement branch.

The authority baseline is now concrete: the number-585 wrapper returned `1`, `setuid(0)` returned `EPERM`, and UID remained `1`. The jail-status `sysctl` query did not supply a value. A later claim of escape requires an independently observable boundary change, such as a changed credential or newly readable protected resource, after a candidate action. `/dev/null` was missing, not denied; `/dev/dmem0` allowed open but returned `ENODEV` on generic read.
