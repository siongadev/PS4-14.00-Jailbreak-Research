# Firmware 14.00 History primitive: native pointer-vector effect

A forged `Uint8Array` over a small resizable buffer can read and write a measured slot formerly occupied by a separately cloned fixed `ArrayBuffer`. The fixed buffer is released with an unreturned `structuredClone` transfer. When the DOM tree is built **before** that release and `querySelectorAll("span")` runs afterward, the released slot can hold the retained result vector.

On the retail console reporting firmware 14.00, [capture `4215e4f7ed054145b4c07c93361532de`](../captures/4215e4f7ed054145b4c07c93361532de.json), SHA-256 `71db251e53973c4449bfe8edde0254bc12901f62e8a5f42004c70ec89a9a0e7d`, source SHA-256 `84c5637b8fdccf1be16f617f27dd7e24d353b04a64dc77d98b18127c117e5482`, recorded:

- A 65,536-byte live fixed-buffer alias beginning at forged-view index 65,528; the normal view became length zero after the unreturned transfer.
- Four adjacent pointer-shaped 64-bit values at the released slot, spaced by `0x70`.
- A write of the second eight-byte value over the first read back exactly as written. During the write, `list.item(0) === list.item(1)` and an adjacent-duplicate scan found index zero.
- Restoring the original eight bytes made `list.item(0)` return its original first node again.

The capture passed `python -m fw14lab.verify`. A fresh-page repeat with the **same source hash**, [capture `0a5870d1c8a4477fa428ff674e2dbd77`](../captures/0a5870d1c8a4477fa428ff674e2dbd77.json), did **not** reproduce the live-list effect: the candidate bytes accepted the write, but no list entry changed. The effect is therefore intermittent. The successful run shows a controlled change to a **live native pointer array**, with both source and destination pointers taken from valid nodes in that same array. It is stronger than reading pointer-shaped bytes, but it is not an arbitrary-address read/write primitive or WebKit code execution.

A size-matched variant used a 66,224-byte fixed buffer, matching the source-predicted capacity of 8,278 pointers for an 8,192-element result list. [Capture `ace0482b0cd14e6d8580eac269e8597b`](../captures/ace0482b0cd14e6d8580eac269e8597b.json), SHA-256 `00cac1ce021bb5b10974df75dee43f4548135d75b8a805cb2445fe7c73f6d202`, again changed `item(0)` to node 1 and restored it, at forged-view index 65,528. The same source's immediate [repeat `59d88f255d874c58b5d53d62bc407491`](../captures/59d88f255d874c58b5d53d62bc407491.json) found candidate bytes at index 155,640 but no live-list change. The exact slot placement, not just requested allocation size, appears important. This is an inference from two captures, not a known allocator rule.

The negative controls matter. When the DOM fragment was appended **after** releasing the fixed buffer, [capture `82f2f60759e448d3969b4ae151a8c29d`](../captures/82f2f60759e448d3969b4ae151a8c29d.json) found pointer-shaped bytes and restored a swap, but `item(0)` did not change. [Capture `4980149028b34bc98e875cd50e978652`](../captures/4980149028b34bc98e875cd50e978652.json) confirmed the write read back while a scan of all 8,192 list entries found no duplicate. This is consistent with observing a temporary allocation rather than the retained list. A fresh-page [guard-buffer control](../captures/f5a8dc47d1714be78ee98cee2e6dc6ca.json) showed the freed slot can instead be reused by another fixed buffer.

The source-guided hypothesis comes from WebKit's [`SelectorDataList::queryAll`](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/dom/SelectorQuery.cpp), which moves a `Vector<Ref<Element>>` into a `StaticElementList`, and [`StaticElementList::item`](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/dom/StaticNodeList.cpp), which returns an entry from that vector. The exact PS4 browser binary has not been matched to this source revision. The before/after JS identity check is the device-level evidence that the modified bytes were live in this run.

The same-slot reuse also tests an allocator-separation assumption. In the reviewed source, a fixed [`ArrayBuffer` backing store](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/JavaScriptCore/runtime/ArrayBuffer.cpp) uses `Gigacage::Primitive`, whereas [`Vector` storage](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WTF/wtf/Vector.h) defaults to `VectorBufferMalloc`, which is [`FastMalloc` unless heap-breakdown instrumentation is enabled](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WTF/wtf/Forward.h). The 14.00 browser-level identity change shows that these two concrete allocations can occupy the same measured slot in this run. That is inconsistent with *effective strict separation between these allocation classes* under this source model. It does not identify the PS4's Gigacage compile setting or prove that every native allocation is reachable from the forged view; Sony may use different code or allocator configuration.

## Two measured slots

A separate [two-slot capture `1b9b5865eb3f4e52b1dd5146f4cca6f6`](../captures/1b9b5865eb3f4e52b1dd5146f4cca6f6.json), SHA-256 `a9a668b190a669bc15ddad8ca88b66096de6197ee53fad4c0c11491bc20f8d6c`, found a 65,536-byte fixed buffer at forged-view index 65,528 and a 66,224-byte fixed buffer at 131,064. After releasing the first and appending a fragment containing one text node followed by 8,191 spans, its first four pointer-shaped words began with `0x00000002009B0AA8`, then `0x0000000201C76DF0`. After releasing the second and querying the spans, the retained list's first pointer-shaped word was exactly `0x0000000201C76DF0`. A valid pointer swap in that second slot made `list.item(0)` return `list.item(1)`, and restoration reversed it.

The matching second/first words link the temporary fragment vector to the retained element list: the temporary vector's first word is a strong candidate for the text node's native pointer because the text node was appended first. The source path for fragment insertion uses a temporary `NodeVector` in [`ContainerNode::appendChildWithoutPreInsertionValidityCheck`](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/dom/ContainerNode.cpp). A fresh-page repeat with the **same probe source** confirmed the same relationship and reversible live-list swap: [capture `8024ec6ec5684978aec552678dee7ca0`](../captures/8024ec6ec5684978aec552678dee7ca0.json), SHA-256 `2fba194540a15f2bd8a421b432eb7c49ed7e8f98df6e5249280609382917912f`. The user reported no memory warning and a responsive page.

## Text-node pointer substitution

A minimally changed two-slot probe saved the forged view and node references **only after** a successful valid-element swap and restoration. [Capture `00edf02d4ddc4290b2e9c4a8e848ef07`](../captures/00edf02d4ddc4290b2e9c4a8e848ef07.json), SHA-256 `0b5eed054e17478c4e3d0b916570f521df5e87a428ccadabca70e00789a76fd7`, source SHA-256 `d0b7ca31f431f8cffa33d147511739127064d18f7dc9ef503eaa3c6c0217cacb`, found both measured slots, the matching pointer word, `swapped: true`, and `restored: true`.

The separate [follow-up capture `e58358e6b1d043458fdc65325206f36c`](../captures/e58358e6b1d043458fdc65325206f36c.json), SHA-256 `34dc27e0b15da1dba45b1a9f88ea99500d15371331fd6d5e52429da3567a770c`, source SHA-256 `002f1b088ffc329eb9d8b37375d944740266df44cc33f24a25d3ed3561c85b3c`, first checked that the retained list still returned its original element and that its pointer bytes still matched the saved value. It then inserted the temporary vector's first word into the retained list's first entry. During the write, `list.item(0) === textNode`, with `nodeType === 3` and `nodeName === "#text"`. Restoring the eight bytes restored the original `item(0)` identity and byte sequence. Both capture hashes verified locally.

The same-page pair repeated in [hold capture `0ff126bf5b014807b7ab1f7006cbfb11`](../captures/0ff126bf5b014807b7ab1f7006cbfb11.json) and [follow-up capture `7eba2dd8bd774403befdaccb63996516`](../captures/7eba2dd8bd774403befdaccb63996516.json). After a page refresh, the same source hashes again passed in [hold capture `1cfb6618c4c54ac3a80bd6d11b9b41ce`](../captures/1cfb6618c4c54ac3a80bd6d11b9b41ce.json), SHA-256 `3dab6752eb80b47ac222450aea3fc228311e768a68f496ea4c24747c4ac0fc3f`, and [follow-up capture `492088a98e414b60bd02a8b7ba04696f`](../captures/492088a98e414b60bd02a8b7ba04696f.json), SHA-256 `eecd07760ba203023a1ed3866e16d364a400c59e1e43d954f81b5e14257d2c3d`. The operator reported no memory warning after the first pair and a responsive, reconnected page before the fresh repeat.

This establishes that the candidate word was the live Text node's pointer, and that a controlled pointer substitution crosses the list's element-type invariant. It does **not** itself demonstrate code execution or arbitrary-address access. The source-guided next question is what happens when the list releases its retained entries: [`StaticElementList`](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/dom/StaticNodeList.h) stores `Vector<Ref<Element>>`, and [`Ref` destruction](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WTF/wtf/Ref.h) calls `deref()` on each current pointer. The exact PS4 binary is not source-matched, so this remains a hypothesis until tested on the device.

## Matched list-release comparison

On the same 14.00 page, the unchanged-list control used [hold capture `3aad3b2056a04d0b9e8e5fbaee9abe46`](../captures/3aad3b2056a04d0b9e8e5fbaee9abe46.json), [release capture `98ce074d0fe346f9b01fcd98f13be035`](../captures/98ce074d0fe346f9b01fcd98f13be035.json), and [observation capture `f4eb33bd9637420cb9171d824fa9b8fc`](../captures/f4eb33bd9637420cb9171d824fa9b8fc.json), SHA-256 `b5e1271ac3973d5bd6f55202e820de1c9ee8e342f9cb6fe9f89bd3ecf579f2d7`. The Text node was detached from its parent before releasing the otherwise unchanged list. Five bounded GC-pressure batches left the list's `WeakRef` dead and its `FinalizationRegistry` callback fired; the rooted Text wrapper still returned `data === "text-probe"`, `nodeType === 3`, and `parentNode === null`.

The modified-list comparison used [hold capture `a7fc74d8abfb4e769bdc1d2434096afb`](../captures/a7fc74d8abfb4e769bdc1d2434096afb.json), [release capture `59cefbb6ff864daaa5e7ed54e69e0369`](../captures/59cefbb6ff864daaa5e7ed54e69e0369.json), and [observation capture `63867c6386a5436688e7c44a15aecc24`](../captures/63867c6386a5436688e7c44a15aecc24.json), SHA-256 `70081f5881e70236241679013161b3ceb294b5f0ad04fb902e84bd8f3ad19543`. It detached a fresh Text node, replaced the retained list's first pointer with that Text pointer, and confirmed `list.item(0) === textNode` before releasing the list. The same five GC-pressure batches again finalized the list. The rooted Text wrapper then returned `data === ""`, while `nodeType === 3` and `parentNode === null` remained readable. All six raw capture hashes verified locally.

The changed data is consistent with the source-predicted extra `deref()` and a dangling native Text wrapper, but a single property difference does not prove the allocation was freed or reused. A queued 512-Text allocation check was **not claimed** because this page stopped polling after the saved result. It must not be counted as an executed test. The matched comparison needs a fresh-page repeat before this is promoted to a reproducible lifetime primitive.

## Absolute-address limit of the saved pointer captures

An audit of all five saved `clone_history_two_slot_hold_v2` results found the same measured slot indices, 65,528 and 131,064, and in every result the temporary vector's second pointer equalled the retained list's first pointer. Each valid-element swap and restoration succeeded. This confirms the *relative* placement and the object-pointer correlation across two page sessions; it does not reveal the absolute address of either slot.

Let `V` be the unknown native address of forged-view index zero. The two slot addresses are `V + 65528` and `V + 131064`. The disclosed Element and Text pointers identify native objects, but no saved field says either pointer is the address of a slot or gives a known offset from one. Even five identical index pairs leave `V` undetermined. A future freed-slot metadata word would be useful only if an independent relationship to a measured slot were verified; a pointer-shaped value or page-alignment guess alone cannot establish process-wide addressing. This is why the [next run](HISTORY_NEXT_DEVICE_RUN_14.md) separates metadata sampling from any address-calibration claim.
