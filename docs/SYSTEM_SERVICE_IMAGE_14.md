# Live 14.00 system-service code and reachable status IPC

This record uses the connected retail PS4 whose operator checked **System Information: 14.00**. The page session `70f88a40719c4399a366ad3e30265d84` reported the `PlayStation 4/14.00` user agent and browser PID `145`. The user-agent string and entered firmware label are observations, not a cryptographic firmware attestation.

## Image attribution and preservation

The [module inventory](LIVE_MODULE_INVENTORY_14.md) named handle `49` `libSceSystemService.sprx`. A guarded info-ex query returned the same name and ID in [capture `739c120693c343e6897efc0df3ba450c`](../captures/739c120693c343e6897efc0df3ba450c.json). Its 424 raw bytes are [preserved](../evidence/live/system_service_info_ex_14.00.bin), SHA-256 `4f14604e6948967538a56b58dd2dbc4a092ff8098e98e3b98700e717fb789b98`. The returned size field and segment count were zero, so historical field labels are not assumed to match this ABI. Three pointer-like words fall inside the independently measured RX mapping `0x83711c000–0x837158000`; the word at offset `0x110` equals the mapping start. [Decoded record](../evidence/live/system_service_info_ex_14.00.json), [VM-map capture `1b3e6247f3244ccbb89fb00c8b6d457d`](../captures/1b3e6247f3244ccbb89fb00c8b6d457d.json).

The complete 245,760-byte RX mapping was recovered through **107 distinct, bounded, hash-pinned browser reads** in that session. Each capture checked the measured process identity and restored the temporarily changed typed-array pointer; the collector rejected duplicate parts and gaps. An earlier independent sample of the first 64 bytes matched the reconstructed image. The [raw image](../evidence/live/rx_0x83711c000_14.00.bin) has SHA-256 `8dfeb423c92508348e6da8e75fdaf2d71fd4e5e3a09d6a73e3883da512213e05`; its [sidecar](../evidence/live/rx_0x83711c000_14.00.json) lists every capture ID and the sample. The first and final chunk captures are [`b307f64f8d1144d3af46de375b696c30`](../captures/b307f64f8d1144d3af46de375b696c30.json) and [`fb755e2b7e7840c592b443efbfa34b0d`](../captures/fb755e2b7e7840c592b443efbfa34b0d.json).

For offline disassembly only, [`build_system_service_elf.py`](../tools/build_system_service_elf.py) wrapped the RX bytes at their measured virtual addresses. The [synthetic ELF](../evidence/live/rx_0x83711c000_14.00.synthetic.elf) is not a shipped Sony binary or complete module. Ghidra's output is retained as [boundary](../evidence/live/system_service_boundary_analysis.txt), [selected functions](../evidence/live/system_service_selected_analysis.txt), [IPC implementation](../evidence/live/system_service_ipc_analysis.txt), [status IPC](../evidence/live/system_service_status_ipc_analysis.txt), [LNC initialization](../evidence/live/system_service_lnc_init_analysis.txt), [webapp path](../evidence/live/system_service_webapp_analysis.txt), and [launch request](../evidence/live/system_service_add_process_request.txt) analysis. Function names assigned by Ghidra are descriptive placeholders; strings and call instructions come from the live 14.00 bytes.

## Device checks

The live code has a function at `0x837147120` called from two service-initialization paths, next to a log string naming `sceSblACMgrCheckNonsecureWebcoreProcess()`. Its first 16 bytes were matched against the captured image and rechecked on the device by the [v13 caller](../probes/clone_history_native_invoke_install_v13.js), which passed its PID and restoration controls in [capture `717cab63e38643739ab6e450d392e1f0`](../captures/717cab63e38643739ab6e450d392e1f0.json). Calling this function once with argument `0` returned **`1`**, then a separate native PID call again returned `145`; the caller restored its modified pointers. [Probe](../probes/clone_history_service_process_gate_v1.js), [capture `d324a9a445144156bb58dd7c75283a2a`](../captures/d324a9a445144156bb58dd7c75283a2a.json). In the two analyzed initialization functions, `0` selects ShellCoreUtil and AppMessaging initialization; `1` selects a log branch. This is a branch observation, not proof that all system-service facilities are inaccessible.

A separate live function at `0x8371206d0` is identified by its embedded `sceSystemServiceGetAppStatus` log string. The [v14 caller](../probes/clone_history_native_invoke_install_v14.js) byte-checked this function and 20 other targets, then passed four PID controls in [capture `22aeecffadf245e7923d33f736582834`](../captures/22aeecffadf245e7923d33f736582834.json). The first read-only status probe reached its return marker, but the collector rejected its result because an array appeared in a detail field; [capture `bc5230384d054a9ebdbe6c592a8f8397`](../captures/bc5230384d054a9ebdbe6c592a8f8397.json) is **not** evidence for the numeric result. The corrected [v2 probe](../probes/clone_history_service_app_status_v2.js) returned **`0`** and changed an owned 12-byte output sentinel to `011700600001006001000000`; it restored those owned bytes and the native caller, and the following PID call returned `145`. [Capture `42c28bbdbf7b4cdeb1beafd3dfc4c266`](../captures/42c28bbdbf7b4cdeb1beafd3dfc4c266.json). The three little-endian words are `0x60001701`, `0x60000100`, and `1`; their semantic field names have not been verified.

The live code explains why these two observations coexist. LNC initialization (`FUN_837121890` → `FUN_8371220f0`) occurs **before** the process-type branch in both analyzed service initializers. The successful app-status path passes an initialized-client check and invokes a virtual request method with selector `0x30013` and a 12-byte response buffer (`FUN_837122560` → `FUN_837128aa0`). The device result establishes a reachable, read-only `SceLncService` client operation from this browser process. It does not establish that arbitrary requests are authorized, that the returned status was privileged, or that the browser sandbox was escaped.

## Process-launch request controls

The same live image contains code and strings for `sceSystemServiceLaunchApp`, `sceSystemServiceLaunchWebApp`, `/common/lib/webapp.self`, and `/system_tmp/sp-webapp-event-socket`. The [webapp function](../evidence/live/system_service_webapp_analysis.txt) passes a path and output descriptor into the LNC `addLocalProcess` client function at `0x837122e80`. The [request builder](../evidence/live/system_service_add_process_request.txt) uses request selector `0x30004`. These are 14.00 live-code observations; the server-side authorization checks are not in this captured browser module. The caller-list analysis found no internal reference to the status or webapp entrypoint, consistent with externally callable service functions, but the synthetic ELF omits export metadata. [Call references](../evidence/live/system_service_callers.txt).

The [v15 caller](../probes/clone_history_native_invoke_install_v15.js) checked the live 16-byte `addLocalProcess` entry and passed four PID controls in [capture `ed8b18f87033421fa3a6cc3577070d5f`](../captures/ed8b18f87033421fa3a6cc3577070d5f.json). Three one-call controls then used owned argument buffers. Subsequent disassembly showed that their 40-byte fifth argument is an **input parameter structure**, not an output buffer; the two non-null-path controls initially filled it with `0xA5` and therefore cannot isolate path or authorization policy.

| Input | Returned low word | Parameter block after call | Evidence |
| --- | --- | --- | --- |
| Deliberately nonexistent executable path, malformed parameter | `0x8094000F` | Sentinel unchanged | [Capture `1c5a7ac3202d4e299a9a14c9562345fe`](../captures/1c5a7ac3202d4e299a9a14c9562345fe.json) |
| `/dev/random`, malformed parameter | `0x8094000F` | Sentinel unchanged | [Capture `9cfd61a7db95401d8f33ca5f6cf3bef8`](../captures/9cfd61a7db95401d8f33ca5f6cf3bef8.json) |
| Null path, which the captured client code rejects before request dispatch | `0x80940005` | Sentinel unchanged | [Capture `d5160c03448d4577ba5e8999ddb1a722`](../captures/d5160c03448d4577ba5e8999ddb1a722.json) |

Every run returned, restored the modified browser and owned bytes, and passed a following PID call. The distinct null-path code confirms that the two non-null paths progressed beyond the client's first argument guard. Because their 40-byte input structures were malformed, the identical `0x8094000F` cannot be attributed to the paths. The captured client function contains no immediate `0x8094000F` in its body; the code also appears in unrelated LNC client functions, so assigning it a 14.00 error name from those occurrences would be unsound. No process launch or socket mutation was observed or claimed.

The webapp function passes the low 32 bits of its app-status response as the add-process app ID. A matched [invalid-path probe](../probes/clone_history_service_invalid_process_appid_v1.js) obtained that ID from a fresh status call in the same command, then sent a nonexistent path. It still returned `0x8094000F` with the malformed parameter, restored its buffers, and passed the PID control. [Capture `14301b38c51c411b9a118f849b35b3dd`](../captures/14301b38c51c411b9a118f849b35b3dd.json).

The captured webapp caller loads a 16-byte constant at `0x837148810` (`size=0x28`, `version=1`, an eight-byte `-1`), writes another four-byte `-1`, then zeros the following 16 bytes before passing the parameter pointer. [Decompiled caller](../evidence/live/system_service_webapp_analysis.txt), [request builder](../evidence/live/system_service_add_process_request.txt). A corrected [v2 invalid-path probe](../probes/clone_history_service_invalid_process_appid_v2.js) used the status-derived app ID and these observed parameter fields, zeroing the final four bytes of the 40-byte block because their value was not established from this caller. It still returned `0x8094000F`; the parameter block stayed intact and the PID control passed. [Capture `8c5cc7af105841798e54b1231eed6982`](../captures/8c5cc7af105841798e54b1231eed6982.json). This rules out the missing size/version fields and app ID `0` as sole explanations for that result. The final four parameter bytes and server-side validation remain limits; the result still does not distinguish path policy, app-context state, and caller authorization.

## Read-only request comparison

The [live service code](../evidence/live/system_service_process_list_analysis.txt) also implements `sceSystemServiceGetLocalProcessStatusList2` with a client-side maximum of 16 entries. Its request builder uses selector `0x3000F`. The [v16 caller](../probes/clone_history_native_invoke_install_v16.js) byte-checked the function entry and passed four PID controls in [capture `a41c3f13c28044c0b34b205a6427fb5c`](../captures/a41c3f13c28044c0b34b205a6427fb5c.json). A 16-entry [read-only query](../probes/clone_history_service_process_list_v1.js) returned `0x8094000F`, reported zero entries, left all 576 output bytes at their sentinels, preserved the buffer guards, and restored state. [Capture `9c7dbc75ab694d13b194c75e051d5e9c`](../captures/9c7dbc75ab694d13b194c75e051d5e9c.json). No process list was obtained. [Request decompilation](../evidence/live/system_service_list_request_analysis.txt).

The [v17 caller](../probes/clone_history_native_invoke_install_v17.js) then checked a read-only `sceSystemServiceGetAppType` entry in [capture `efd48e7cbc02487b8726b7b616108b5d`](../captures/efd48e7cbc02487b8726b7b616108b5d.json). Queries for the first and second 32-bit words from a fresh app-status response both returned `0x8094000F` without changing the owned type output, while PID controls and restoration passed. [First-word capture `f9e1a69abdfb44aa904e271f7070ae5b`](../captures/f9e1a69abdfb44aa904e271f7070ae5b.json), [second-word capture `9b3beaef9e934d52b8268cce34c111e2`](../captures/9b3beaef9e934d52b8268cce34c111e2.json). The two words are not yet proven to be valid inputs for this particular API. The common error across status-list, app-type, and invalid add-process requests points to a shared service or app-context condition, but its meaning remains unverified.

## Offline selector inventory (2026-10-22)

A byte scan of the preserved RX found request-builder selector immediates `0x30000` through `0x3004B`, plus `0x30070` and `0x300DE`, at `0x837128185`–`0x83712a2f5` (the builders start around `0x837128130`). The tested subset is still `0x30013` (status, succeeds), `0x30004` (addLocalProcess, `0x8094000F`), `0x3000F` (process list, `0x8094000F`), and `0x30010` (loadExec, not called). The client library contains the request shapes but not the server policy; the remaining selectors cannot be classified as permitted or denied offline. Do not enumerate them on-device without a server-side discriminator.

## Next discriminator

The [public PS4 error-code table](https://www.psdevwiki.com/ps4/Talk:Error_Codes)
labels `0x8094000F` as `SCE_LNC_UTIL_ERROR_NOT_ALLOWED`
(CE-32879-9). That name fits the repeated launch, process-list, and
app-type results, but the table does not prove the exact 14.00
server-side predicate. The live browser-side add-process request builder
does not itself return this immediate, so a service-side denial is a
plausible inference. Further path or parameter changes lack a useful
prediction until an app-context or capability change is measured.

The active LNC status route and reachable add-process request make this a concrete service boundary. A [fully specified built-in launch check](WEBAPP_LAUNCH_GATE_14.md) is now complete: the 14.00 path prefix resolved to `uW0gp3J1i0`, the resulting `webapp.self` opened read-only, and Sony's own `sceSystemServiceLaunchWebApp` sent one request with `about:blank`. It returned `0x8094000F` and stored that error instead of a process ID; no launch was observed. The code for the add-process client does not contain this error immediate, so its exact source is downstream of that function's initial argument checks. The same result from process-list and app-type queries is consistent with the public `NOT_ALLOWED` label, but the 14.00 server-side cause remains unverified. This route is parked until server-side 14.00 evidence or a distinct effect oracle separates authorization from app-context and transport failure. Repeating equivalent paths or launch arguments will not resolve the ambiguity. No unauthorized action, sandbox escape, kernel code read, or protected-resource read has been shown through this interface.
