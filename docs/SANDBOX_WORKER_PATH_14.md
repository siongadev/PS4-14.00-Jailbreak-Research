# 14.00 worker-side native-call path

Updated 2026-10-20. This is an independent implementation in the current project. The older project's 14.00 worker observations supplied only a hypothesis about transfer layout; every address and pointer used below was rediscovered on the connected 14.00 page. No older-firmware address was used.

The first [transport capture](../captures/af92a6a9d25448de9dfd233eff53932b.json) confirmed that a Blob-backed Worker returned an intact two-word typed array in 9 ms. A [read-only transferred-buffer capture](../captures/1532f39b694c44078bca3b4cd83c4ed1.json) followed its live `ArrayBuffer` cell through an implementation pointer to the backing address and matched all four worker-created marker words; the page's temporary read pointer restored.

The initial fixed-link assumptions did not pass. [Layout v1](../captures/281f0dbff0314c1789d691de4f41e96a.json) and [layout v2](../captures/c89cf0f502a84b938b693a4c32c75cae.json) stopped at an invalid candidate butterfly. [Read-only link captures](../captures/09eca03e665648708022d33ebfd4be9e.json) and [link v2](../captures/d631265a6d9b4c2bae003e70aeb24631.json) exposed a path back to the marker's own bytes, which is not a worker-object location. Explicitly allocating the 16-byte marker and sending a ping before the transfer yielded a plausible butterfly, but checking only three fixed slots [missed the object shapes](../captures/a4e016483115450eaa3d954dff44278f.json). The bounded eight-slot [shape scan](../captures/bd3de7f027a4454b9647b4198c4ea327.json) found a one-property object at index 2, a length-6 `Uint32Array` at index 3, and a length-48 `DataView` at index 4, with the main-page read pointer restored. These are page-local observations, not universal offsets.

The next [owned-memory capture](../captures/25303a3b76e64caf962afc2e2e91e4d5.json) temporarily pointed the worker's six-word typed array at its own DataView cell. The worker then used indexed writes to redirect the DataView to the transferred marker and returned the exact four marker words. The capture reports both worker vectors and the main-page read pointer restored. No native call occurred in that check.

The worker's `Math.expm1` object and metadata were then read through its own wired DataView. Its slot address differed from the page's slot, so an address-equality check [failed](../captures/69c697d89edf4dd094473709ed049b68.json); this was a wrong preflight assumption, not a failed worker read. A [byte comparison](../captures/d8b71e108855486ba5a22e0c1a41c9cb.json) found exactly one worker-specific metadata slot containing the same original call-target bytes as the page plan. A [worker-owned pivot object](../captures/54c06ba9310d4e76b7395c52b1e388e6.json) was located and its header read without changing it. Both checks restored the worker vectors.

One bounded [worker-side number-20 call](../captures/3b95e94baaef4c60bc70ef6252f78a31.json) then rechecked the live gadget bytes, current owned chain, worker slot, worker pivot header, and output sentinel. It temporarily redirected the worker-specific callable slot and pivot header to the already owned native plan. The worker called `Math.expm1` once; the owned frame changed from `0xa5` bytes to PID **145** with high word zero. Both authenticated markers, `worker_getpid_preflight` and `worker_getpid_restored`, arrived, and the capture reports the worker slot, pivot, frame, two worker vectors, and page read pointer restored. The exact pinned source is [worker getpid probe](../probes/clone_history_worker_getpid_v1.js). The capture's SHA-256 is `b4d4225c43891036a78f54141c983efb6618f200fd07739786656ed1d417c6c9`.

This established a second browser thread capable of a controlled benign native call in the current project. The concurrent-call and event-queue controls later in this file advanced that baseline. They do not establish an event-registration race, changed credentials, kernel memory access, or a sandbox escape. The earlier 14.00 race replay did not prove that registration overlapped descriptor close inside the kernel.

To make that overlap test possible, the project allocated a **second, non-overlapping** store, pivot, stack, and output frame. The first builder [stopped before construction](../captures/a686b33f5cfc400b8306ba5a3e793dc4.json) because a new 32-byte typed array had zero at cell offset 8. [Its cell bytes](../captures/3686b10dcb5d4d43ba68f2b8094db8ae.json) showed a plausible vector at offset 16 and length 32 at offset 24. A live-vector gate then matched canaries at offset 16 for all four new arrays, but [readback differed](../captures/56d66cb57a4e46f0ad2d07c52feea289.json) for the two smallest buffers after `DataView(buffer)` was created. Materializing all four backing buffers *before* measuring their vector addresses fixed that: [independent-plan capture](../captures/79d65351f89a49c285f215fb5584cff7.json) reports four offset-16 vectors, no overlap with the page's plan, matching bytes in each owned buffer, and restoration of the temporary read pointer. These failures are retained because they explain why pre-materialization addresses cannot be assumed stable on this page.

One further [worker call using only the second plan](../captures/f5509507ccd04e838bee9700c67e3b5e.json) returned PID **145** with high word zero. Its preflight/restoration markers arrived, and the capture reports the worker-specific function slot, pivot header, output frame, two worker vectors, and page read pointer restored. [Exact pinned source](../probes/clone_history_worker_getpid_independent_v1.js). This was sequential validation of a separate plan before the overlap check below.

A bounded [worker sleep control](../captures/4b27c13071514479ba52fe0c9784550e.json) located the live number-240 wrapper by its exact current-process bytes, checked the required gadgets, and used the separate worker plan for a 300 ms native sleep. The page's 50 ms timer fired before the worker's return timestamp; the native return was zero and every changed pointer and owned byte range restored. [Exact pinned source](../probes/clone_history_worker_sleep_overlap_v2.js), SHA-256 `0bee7bfb2be46542aa1e98138d3ab5596ade0ed6e1fc916c622d3f6370c1499a`. The first version [stopped in preflight](../captures/dcb114a1bd2a489bb4fc998180bf0a73.json) because its read helper rejected two-byte gadget checks; it made no sleep call. This establishes that page JavaScript advances while the worker is blocked in a native call.

The next [dual-native capture](../captures/8fde7c10e65845a7922805ced25792a1.json) used the worker's 300 ms sleep and made a page-side number-20 call with the original page plan while the worker was blocked. Its timestamps show the page call at 53 ms after worker entry, returning within the same clock millisecond, and the worker returning at 300 ms. The page returned PID **145**, the worker sleep returned zero, and both plans restored. An [independent repeat](../captures/9fcd312ffce4498182b488e8b0b6c2c1.json) placed the page call at 52–53 ms and worker return at 301 ms, with the same results and restoration. [Exact pinned source](../probes/clone_history_worker_dual_native_v3.js), SHA-256 `aab87a834ddaf6d3b6c7d398a23ace7e1c80c8d35a67db0e467801353a47beab`. An earlier report [exceeded the collector's detail limit](../captures/a4b7c334ce794c9d953644b96e335ae8.json), and the next [captured both native results but used a strict greater-than millisecond comparison](../captures/db9e1c23938f49bfb5af6f0f664788e8.json); neither was counted as an overlap pass. The two valid timestamped runs establish overlapping benign native calls from separate browser threads. They do not test event-queue registration, descriptor reuse, kernel state, or sandbox escape.

A guarded [page-side caller](../probes/clone_history_native_invoke_install_v1.js) now checks four live wrapper signatures and ten gadget signatures on each page before installing an allowlisted call helper. Its first `getpid` returned PID **145**, with both authenticated markers and carrier restoration: [capture](../captures/679ce29302984f299c6d9cfb2b539491.json). Using only that caller, the [owned user-event round trip](../captures/fd8bc851a1cc419299998955f3e4e9d8.json) opened queue fd `9`, added and triggered identifier `1`/filter `-11`, read exactly one matching 32-byte event into a guarded 64-byte output, deleted the event, and closed the queue. All return codes and byte restoration checks passed. This reproduces the old project's *14.00* ordinary user-event behavior independently in the new project.

The worker-side [event wait/wake capture](../captures/99d39287102642d3b848e87814066327.json) then registered that event on the page, entered a two-second maximum number-363 wait from the worker's separate native plan, and triggered the event from the page after 50 ms. The worker returned one matching event after 52 ms; its 32-byte output guard, worker pointers and buffers, event deletion, and queue close all passed. The [same pinned probe repeated](../captures/7ce7d9b2dfd8443eb2fe66a41b99e3b5.json) with the same 52 ms result. [Exact source](../probes/clone_history_worker_event_wake_v2.js), SHA-256 `93444d047fd7bb08cc184992f0eb5c27cc56313b9f9bc75a9d8bbcb42717a65e`. The first version [stopped before the native wait](../captures/207bef69416c40998a25c5d8c0cae8c5.json) because the worker plan's result frame was 64 bytes; v2 allocated separate owned 64-byte output and 16-byte timeout buffers. These are normal, source-specific event controls. They establish the concurrent interface and cleanup needed for a registration-versus-close/reuse discriminator, but they do not show the race or a sandbox boundary change.

The [guarded page caller v2](../captures/3090ce01effb467ca01a97ff8112b02a.json) additionally rechecked the live number-4 `write`, number-41 `dup`, and number-135 `socketpair` wrapper bytes before exposing those calls; its PID-145 control and carrier restoration passed. [Pinned v2 source](../probes/clone_history_native_invoke_install_v2.js), SHA-256 `07e23cbf1112865f646f52d8c0459511c1e4ac8cfecc97b4aaed391a2c299795`.

Three sequential socket controls then passed on the same 14.00 page. The [readiness capture](../captures/00ff1166c66d409ea43b4db354905a5e.json) opened queue fd `9`, socketpair fds `10`/`11`, duplicated read fd `10` to `12`, registered fd `10`, wrote one byte through fd `11`, and read exactly one matching `EVFILT_READ` event; its guard, deletion, closes, and owned-byte restoration passed. [Pinned source](../probes/clone_history_socket_readiness_v1.js), SHA-256 `08f1b72501b2e83a45e942e8e88b7b09d29190f3f0b6d4f81647e9239575b527`. The [alias-close capture](../captures/4db9593bb54545b6be985c8bd4bed098.json) registered fd `10`, closed that number while fd `12` retained the old socket, wrote to the old socket, and got **zero** events; registering fd `12` then gave one matching event. [Pinned source](../probes/clone_history_socket_alias_close_v2.js), SHA-256 `b333e8b82647b74fccda77dd19212a4dd5888cc7376730493abc85f87b0557fe`. The first alias-close version reached its preflight and restoration markers but [exceeded the collector's 12-field detail limit](../captures/c54b767f41b6442a817ee35c6340fc0e.json), so its check is not evidence of the event outcome.

The [sequential reuse capture](../captures/f3d08853aef14a2b9a77448bf60fd0a0.json) closed watched fd `10`, opened a replacement socketpair whose read endpoint reused **fd `10`**, and wrote separately to the retained old socket and replacement socket. Neither source produced a stale event. Explicitly registering replacement fd `10` produced one event; explicitly registering old duplicate fd `12` produced one event. All output guards, descriptor cleanup, and owned-byte restoration passed. [Pinned source](../probes/clone_history_socket_reuse_sequential_v1.js), SHA-256 `b85a084b88ac5e10b7cd808936bf5ca9c49bae13499f4721ed680e9d08c32acf`. These controls establish the old-versus-replacement oracle but never overlap registration and close.

The read-only [thread rendezvous capability capture](../captures/2f5903af557c482e8c3caf46de320f2b.json) reports `crossOriginIsolated=false` and `SharedArrayBuffer` unavailable on the current page, despite `Atomics.wait` being exposed. A [second capture](../captures/ef56231f49ef48eb808b6be53c258e95.json) reports `isSecureContext=false` for the console's LAN HTTP page. The present page cannot use a shared atomic barrier to align the two browser threads; isolation headers alone cannot repair the insecure transport. [Race decision plan](FD_REGISTRATION_RACE_14.md).

The [first native continuation capture](../captures/21e8196e390e48d4bb460b110a10e403.json) and [exact-source repeat](../captures/4f9aa43fc4c74ecbbf1bb667f35a9140.json) then used one worker chain to wait in number 363 and, after the page triggered its owned user event, call number 20 **before returning to worker JavaScript**. Both runs returned one matching event and PID **145** with zero high words after 52 ms. The output guard, queue cleanup, worker pointers, frame, stack, and buffers restored. The exact [wait-then-getpid source](../probes/clone_history_worker_wait_getpid_v1.js) is pinned at SHA-256 `ca45d07194a336458ba36bd1502fa81b43157314b45954af94a1cdad52e10964`. This validates a two-call continuation and the page-to-worker wake control; the second call did not register an fd, overlap a close, or cross the sandbox boundary.

The [worker wait-then-register capture](../captures/313fe3e3d8b74f8dbe503a0ad9522d4c.json) and [exact-source repeat](../captures/824ad7f40b6c448f899f8ca7e0aead15.json) replaced the second native call with another byte-checked number-363 call. The worker registered owned socket read fd `10` after the wake, before returning to JavaScript; the page wrote through the peer and read one matching `EVFILT_READ` event. Both runs returned wait `1`, add `0`, a matching user event and socket event, intact guards, and complete pointer, byte, queue, and descriptor cleanup. Each elapsed 52 ms from worker entry. [Pinned source](../probes/clone_history_worker_wait_register_v1.js), SHA-256 `8a061161fa474c9489ff636025d64c6cfee8cc4337b48d64fd793fec4a2056dc`. This is a normal registration control with no concurrent close or descriptor reuse.

The first [wake/register versus close/reuse comparison](../captures/b58ba9361e4545ddaa3a8b0c2f752fe4.json) returned wait `1`, register `0`, close `0`, exact numeric fd reuse, no event from either separately written socket source, intact guards, and full cleanup. Its recorded page close began **after** the worker's return timestamp (`close_before_return=false`). That ordering cannot distinguish a normal removed note from the proposed kernel race; it is a scheduling miss. [Pinned source](../probes/clone_history_worker_fd_reuse_window_v1.js), SHA-256 `7cdf5bb9394972a54370725cdd1dc1bf2303f913fa5443c661219207802f3c76`.

A separate [page three-call control](../captures/d4e3d8386efa429eb8bd0f192bc917ba.json) returned the same PID `145` from three consecutive number-20 calls, with live wrapper and gadget checks and restored page call state. [Pinned caller source](../probes/clone_history_native_invoke_install_v3.js), SHA-256 `27248e124ccf4ab993666b41a4fec4058447068803ef709185737f382c76ebf1`. The revised comparison used that page chain to trigger the user event, close the original fd, and open its replacement without returning to JavaScript between calls. Its [first run](../captures/22303e2f584b42f3872e178661108ca6.json) returned worker add `0`, **replacement source only** signaled, and the page chain returned before worker JavaScript; this is consistent with registering the replacement after reuse. [Second](../captures/fe1eeb654167474fa83e49f9cd57fd67.json) and [third](../captures/288f04ae6a8643bfa50d50937553f669.json) runs returned worker add `-1`, no signal from either source, and the page chain's return timestamp was after the worker's return timestamp. All three had exact numeric reuse, matched user event, guards, pointer restoration, and descriptor cleanup. [Pinned comparison source](../probes/clone_history_worker_fd_reuse_window_v2.js), SHA-256 `c036d8ce2d91234a551075cadd5b0b38d593c8536385a348eb72b9fd1c5d5e91`. The `-1` return's errno was not captured; no run showed the old source signaling, and no run proves overlap inside the kernel's `fget()`-to-lock interval.

The [variable-length page-chain control](../captures/7f7a5e68e0ca472e98f390c29e4efbd8.json) then returned PID `145` from four calls and restored all page state. [Pinned source](../probes/clone_history_native_invoke_install_v4.js), SHA-256 `ba92297545c88eb1e971f6be58bc42ff6d0019366b1fea0cf333abb4d9e53596`. Its first scheduling variant inserted one checked `getpid` call between wake and close while keeping replacement open in the same native chain. Both [first](../captures/abe9058ac1d843cb8dfcb440318936a2.json) and [repeat](../captures/c8f0743ddf614d078793ee3a08612bb8.json) returned delay PID `145`, worker add `-1`, exact fd reuse, no event from either source, and full restoration. [Pinned variant](../probes/clone_history_worker_fd_reuse_delay1_v1.js), SHA-256 `a2f4e14e8dc3b0bb9729dc0ea0ac380a458aa261b76446fa42bb1be7571b0cb8`. This short delay did not create the old-source mismatch, and the worker error's errno remains unmeasured.

A subsequent worker chain recorded the registration result and the same worker's immediate error state before returning to JavaScript. In [one run](../captures/5e99ee54320847d1b7986cc3742f6b1b.json), add returned `-1` with errno `9` (`EBADF`); in its [repeat](../captures/afdf17528ae342b994d5d165c016f3f2.json), add returned `0` with errno `0` and only the replacement source signaled. Both had exact numeric reuse and intact guards, cleanup, and pointer restoration. [Pinned source](../probes/clone_history_worker_fd_reuse_errno_v1.js), SHA-256 `9c1d29e303b4a2650d4bab05440a2bf7fe06572119e1348564f9367072325c7f`.

A [five-call page control](../captures/e4acd0a28de24a85a4d7b135ed3591db.json) returned PID `145` five times and restored its plan. Two comparisons with **two** intervening `getpid` calls again split between [replacement-only registration, errno `0`](../captures/49e372e0e7c04f3b8e07e4122ae0af28.json) and [no registration, errno `9` (`EBADF`)](../captures/cde72007e5a64a7799f45ea6e68458ae.json). Neither produced an old-source event or a warning reported by the operator. [Pinned variant](../probes/clone_history_worker_fd_reuse_errno_delay2_v1.js), SHA-256 `2752fff3d511c83d4aa97e1378714dd3d6cddd6035512eedb0b18a68418b1160`. Small changes in page-side call count did not reliably select an ordering; these outcomes are consistent with ordinary fd reuse and failed lookup and do not identify the narrow kernel interval.
