Use a new connected 14.00 page session for the following order.

The exact-capture audit found five passing `clone_history_two_slot_hold_v2` results across two page sessions; every recorded hold reported `swapped: true` and `restored: true`. The Text-node lifetime change has only one matched comparison. Repeat that comparison first; use the same-type Element branch afterward if the Text result stays ambiguous. These counts describe saved results, not an estimated success rate.

1. Run `clone_history_two_slot_hold_v2`. Proceed only if both measured slots are mapped, the temporary second word matches the retained first word, and `swapped` and `restored` are true.
2. Run `clone_history_list_release_control_v1`, then `clone_history_list_release_observe_v1`. Require `list_finalized: true`, `list_weak_alive: false`, and the detached Text wrapper still returning `text_data: "text-probe"`.
3. On a **new page session**, run the same hold probe, then `clone_history_list_release_sham_v1` and `clone_history_list_release_observe_v1`. This sham detaches the Text node and briefly substitutes its pointer, then restores the list before release. Require `matched_text: true`, `restored: true`, list finalization, and `text_data: "text-probe"`. If this control also changes the data, the earlier difference cannot be attributed specifically to retaining the substituted pointer through destruction.
4. On another **new page session**, run the hold probe, then `clone_history_list_release_mutated_v1` and `clone_history_list_release_gc_only_v1`. The preparation must report `matched_text: true`. The GC-only probe reports list finalization without reading through the potentially stale Text wrapper.
5. If the list finalized, run `clone_history_stale_text_read_v1` to repeat the changed-data observation in a separate command. Record whether the page continues polling after the read. This distinguishes disruption at list collection from disruption at stale-wrapper access.
6. On another clean page, repeat step 4 and run `clone_history_stale_text_reuse_v2` **without first reading the old wrapper**. It sprays 512 uniquely labelled Text nodes and reads through the old wrapper once. Only if that read matches a sprayed node does it write a distinct token through the old wrapper, check the matched live node, and restore the live node's original data. A unique match plus `live_changed: true` and `restored: true` would demonstrate a live native alias. If the write interrupts the page, the durable `stale_text_alias_INDEX` and `stale_text_before_write` markers separate a matched read from the attempted write. An absent match leaves the lifetime mechanism unresolved.
7. **Lower priority after a confirmed same-type alias:** on another clean page, repeat step 4 and use `clone_history_stale_comment_reuse_v1` instead of the Text spray. `Comment` and `Text` both derive from `CharacterData` with no added data fields in the reviewed source, but each declares its own ISO allocation type. A unique Comment value through the stale Text wrapper, especially with `nodeType === 8`, would distinguish cross-type reuse from same-type aliasing. A miss is inconclusive: if the console enables ISO allocation, equal-sized objects of these types may use separate heaps.
8. Lower priority, on a separate clean page: run `clone_history_freed_slot_metadata_v1`. It samples the first 64 bytes of a measured fixed-buffer slot immediately after release, before any deliberate reuse. If the bytes remain the old marker, stop this allocator-metadata branch. Treat changed pointer-shaped words as candidates only; they do not identify the slot's address without an independent match.
9. **Only if step 8 shows a changed candidate word without a memory warning**, use a new page session for `clone_history_free_link_pair_v1`. It maps two 66,224-byte cloned fixed buffers, samples both live headers, releases the second then the first, and captures the first 64 bytes after each release. A prior [14.00 mapping capture](../captures/654492014c004fd2be434218c959a8ba.json) placed the first two buffers of this size at forged-view indices 65,528 and 135,160, so the pair should fit within the existing 262,144-byte scan; the probe still measures both positions anew. It reports raw words and spacing; `pass` means sampling completed, not that a free-list link or absolute address was found. A candidate word must identify another measured slot under one consistent view-base calculation and survive an independent validation before being used as an address. The pinned source SHA-256 is `95ca63d896b5af0f5bda829214b3c2b34b909c64c30bccc6ee483e608a2df01a`, and the canonical manifest SHA-256 is `3e986171d6adcd53adb29cb29081e6059ed8bd3142eef85ad7037973cd19a09d`. It is prepared and syntax-checked, not run on the PS4.

The conditional is source-guided, not a claim about the PS4 allocator. In the reviewed WebKit revision, [fixed `ArrayBuffer` allocation](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/JavaScriptCore/runtime/ArrayBuffer.cpp) calls `Gigacage::tryMalloc`. [Gigacage](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WTF/wtf/Gigacage.cpp) uses system malloc or bmalloc according to the build. In bmalloc's [large deallocation](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/bmalloc/bmalloc/Heap.cpp), the freed range is added to `m_largeFree`, whose [storage is a separate `Vector<LargeRange>`](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/bmalloc/bmalloc/LargeMap.h). That path does not itself predict an in-slot next-pointer. The PS4's allocator branch and exact browser build remain unverified.

The reviewed WebKit source marks `Text` for [ISO allocation](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/dom/Text.cpp), but [`IsoMalloc.h`](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WTF/wtf/IsoMalloc.h) falls back to general allocation when the feature is disabled. The console's build setting is unknown. A same-type Text reuse result would establish a dangling-wrapper effect but would not, by itself, show cross-type reuse or code execution.

The reviewed [`Text`](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/dom/Text.h) and [`Comment`](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/dom/Comment.h) classes each declare `WTF_MAKE_ISO_ALLOCATED` for their own type; [`IsoHeap`](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/bmalloc/bmalloc/IsoHeap.h) is parameterized by that type. This is why same-type reuse and the independent same-type Element branch rank ahead of a Comment spray. The five 14.00 hold captures show adjacent span pointers at `0x70` spacing and Text pointers roughly 7–19 million bytes away, but those addresses alone cannot establish the PS4's allocator configuration.

In the reviewed WebKit revision, [`StaticElementList` stores `Ref<Element>`](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/dom/StaticNodeList.h), [`Node::deref()` reaches `removedLastRef()` at zero](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/dom/Node.h), and [`removedLastRef()` deletes non-Document nodes](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/dom/Node.cpp). This is the source-level prediction the control, sham, and modified runs discriminate; it is not a claim that the PS4 binary matches that revision.
