## Source-level boundary hypothesis

The [pre-fix WebKit deserializer](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/bindings/js/SerializedScriptValue.cpp) chose an 8-, 16-, or 32-bit object-reference index from its current pool size, at `0xff` and `0xffff`. The [2024 WebKit fix](https://github.com/WebKit/WebKit/commit/010c6bdfb0cde0485d31f0260ab9a046fa9b8567.patch) explicitly removed erroneous BigInt additions from that pool. In our graph of outer length `N`, the serializer's reference pool should contain `N−1` objects when it writes the repeated reference; one extra deserializer BigInt entry would make the reader's pool size `N`. This predicts width disagreement exactly at `N=256` and `N=65536`: the writer emits one or two index bytes while the reader consumes two or four. The observed 255/256 transition matches this prediction. The mechanism is an inference from upstream source and our observed graph, not a fingerprint of the PS4 binary.

The aligned run keeps the 65,533-element filler and moves the final array entry from index `0xffff` to `0x10000`, so the low two bytes of the next serialized index are zero. The pre-fix deserializer's extra two-byte read should then leave a valid object-pool index and reinterpret the remaining bytes as a new array index. For the `-64000` tail, this predicts an inserted zero at index `0x50001` and array length `0x50002` (327,682). The live capture matches those values. This is controlled **JavaScript graph corruption during deserialization**; no native-memory read or write was measured in this new run.

Changing the signed integer's second serialized byte from `06` (ZeroTag) to `07` (OneTag) changed the unintended value from zero to one in a fresh session. The 8-bit string case uses StringTag `10`, a StringData length header `00 13 00 80`, two zero bytes, and eight `FF` bytes. The shifted reader interprets those as outer array index `0x100001`, ObjectReferenceTag `13`, pool index `0x8000`, and two array terminators. The chosen filler object appears at that unintended index. The 16-bit string case has header `00 13 00 00`; the shifted reader instead selects pool index zero and creates a self-reference. Two fresh-page captures reproduce the self-reference. These are source-predicted object-graph edits, not yet a native-memory primitive.

## Next primitive decision

The source path for [ObjectReferenceTag](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/bindings/js/SerializedScriptValue.cpp) returns a generic value from the deserializer's pool. Its [typed-array-view path](https://raw.githubusercontent.com/WebKit/WebKit/7841b2790f42d00eb2a8a9357a38d9df5509e047/Source/WebCore/bindings/js/SerializedScriptValue.cpp) checks that a referenced backing object inherits `JSArrayBuffer` before constructing a view. Therefore the successful object-reference and self-cycle probes prove parser control and graph redirection, but do not by themselves establish a typed-array type confusion. The next candidate needs a separate, demonstrated native consumer of the redirected value or a valid backing-buffer view with independently verified bounds behavior. Preserve these captures and avoid treating a generic memory warning as that proof.
