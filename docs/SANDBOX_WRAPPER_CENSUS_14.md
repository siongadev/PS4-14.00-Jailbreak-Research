# Browser syscall-wrapper boundary on PS4 14.00

The live browser page independently read three contiguous 4 KiB code pages around a byte-checked number-20 wrapper. It found **293 unique 15-byte syscall wrappers**: 115 before the anchor page, 117 on it, and 61 after it. The [exact-number capture](../captures/0d7687b41f104aada204059eb3ef9c64.json) preserves every number and the page split; [count control](../captures/bdcbf6797599445080744a9f65da3c56.json) independently returned the same counts. Both probes restored the temporary typed-array pointer.

The three-page region was then checked against a live `sysctl` VM-map record for the executable mapping containing the same number-20 wrapper. The [mapping capture](../captures/3337f5c9422f4cc793e48b03e8c0e3ce.json) measured `0x8169c0000–0x816a14000` (344,064 bytes, RX) in browser PID 71; the [held-range capture](../captures/0fe437ab198242899a573cb427b40346.json) stored that page-local range after a second VM-map check. The [full-range census](../captures/e6f4f536831e40ca9350b2dc83045a14.json) read that entire mapping, rechecked the live number-20 bytes, and restored the temporary pointer. It again found **293 wrappers and 293 unique numbers, with zero wrappers outside the old three-page window**. Numbers `221`, `222`, `510`, `518`, and `571` were absent from the full mapped code segment. This is a survey of that measured executable mapping, not of every browser module or the kernel's syscall table. All addresses are valid only for the measured page.

A second [full-range opcode capture](../captures/74bbb24ed4f447f286b8d48ce0940de8.json) counted all 305 `0f 05` byte pairs in the same RX mapping and preserved the surrounding bytes for the 12 outside the standard 15-byte pattern. Three pairs are embedded in immediate or displacement bytes, rather than being executed as instructions. The other nine have a preceding fixed `mov rax, immediate` for numbers 42, 251, 1, 50, 421, 59, 454, 55, and 340. This mapping did not reveal a variable-number syscall gateway. This classification is based on local byte context, not a full control-flow proof.

This page's address calibration was re-established from a new live object inside the already measured 2 MiB forged-view range: [state check](../captures/e780364109a54ee5a2888a5f10c8d435.json) measured base `0x2018f0000`, object word `0x201ad0140`, property index `1966408`, and a live property. The first allocation probe's output was [rejected by the collector](../captures/10f66c344d72426fb66d82c52e7ec8d8.json) because it used a nested detail value; the separate state check is the valid calibration record. The [owned typed-array swap](../captures/9e2d6e37135542059cec17505ebf217e.json) then passed and restored, and the [native-call plan](../captures/d57e4756d97f4c82b208b1783749e1a0.json) rechecked all 15 gadget signatures against this process. A prior sparse scan had stopped after its 4 MiB milestone with a memory warning and refresh; it provides no base measurement.

For future sessions, the [version-2 anchor probe](../probes/clone_history_inrange_anchor_groom_v2.js) emits only scalar detail fields, matching the collector's schema. A local simulated-success test covers this report shape. Version 2 has not yet run on the PS4; the valid calibration above came from the independent state check.

The generic syscall-tail investigation is now more specific. The [17-word owned-chain dry run](../captures/5576a66691604f6581b811287401a862.json) verified the chain and pivot bytes and restored them without a native call. The [pointer-arm dry run](../captures/7ade9bf79f6c424b82787aa77eaa3f3b.json) ran the same pre-call setup, temporarily armed both native pointers, and restored the chain, pivot, frame, function slot, typed-array pointer, and ordinary `Math.expm1` behavior. The [extended mapped number-20 call](../captures/4ebafb5ad2694498ab55127595464147.json) returned PID `144` through that chain with all fields restored. The [interior of the **same** number-20 wrapper](../captures/40a4b37cb7a9451e91dd7a0fc7c38d0d.json), entered after its `mov rax,20` with RAX separately set to `20`, also returned PID `144` and restored everything.

In contrast, the **same-page** comparison entered the identical instruction suffix inside the number-456 wrapper while setting RAX to `20`: command `88bd2835a1a547deae99f56fd68b7263` emitted `foreign_int_preflight` at 10:27:34 UTC, then produced no return or restoration capture. The operator watched the system-memory warning and page refresh. Its [pinned source](../probes/clone_history_sandbox_foreign_interior_pid_v1.js), SHA-256 `6d11fe78881ff9a77ebde735487295ae4baf42e10dffe0b7c67e9241e1264932`, changes the callsite from the passing number-20 interior control while keeping the number and chain. An earlier mismatched-site command behaved the same way on a different page. This isolates the mismatch between requested syscall number and wrapper site as the leading explanation; the exact faulting kernel instruction is still unseen. [Primary PS4 research slides](https://www.psdevwiki.com/ps4/images/a/a9/02r0.pdf) describe Sony's opcode check: an interior `syscall` entry worked only when the requested number matched the wrapper's preceding `mov rax` immediate. [A separate primary writeup](https://github.com/Cryptogenic/Exploit-Writeups/blob/master/PS4/%22NamedObj%22%204.05%20Kernel%20Exploit%20Writeup.md) also reports wrapper-format and module-range checks. Those older accounts explain the observed pattern, but the exact 14.00 kernel check has not been inspected.

The practical boundary is narrower than “set RAX to any number.” This browser can call its verified wrappers and can enter a wrapper's instruction suffix when the number matches. The full mapped-code inventory offers no ordinary `221`/`222`/`510` semaphore route, and the mismatched-number tail has not returned. A kernel candidate should first be tied to a wrapper actually measured on 14.00 or to another independently verified entry. An upstream FreeBSD advisory alone does not establish Sony's kernel code or browser reachability.
