# 14.00 Web App launch gate

The browser's live `libSceSystemService.sprx` image contains `sceSystemServiceLaunchWebApp` at `0x83711e530`. Its no-argument path-prefix import returned `uW0gp3J1i0` on the current 14.00 page ([capture](../captures/4a4a4fd4f5644f1a89f9e417cc077ac1.json)). The function appends `/common/lib/webapp.self`. The browser then opened that exact path read-only as fd 9 and closed it successfully ([capture](../captures/8cbbce2200284df0a97c7bcd6c25b342.json)). Those observations supply a real path, but not evidence that the process-launch request is authorized.

The next bounded test calls Sony's own launcher once with an owned `about:blank` argument. Its byte-checked entry and four PID controls must pass first. The probe reads the launcher's stored process-ID slot at `0x83715c020`; if it already names a positive process, the probe stops before calling, because the function would kill that prior process. It records the read-only app status before the request, sends a synchronous pre-call marker, and captures the return and stored process-ID slot afterward. If the function reports success with a positive new PID, a signal-zero `kill(pid, 0)` checks existence without delivering a signal. The probe restores its owned argument and status buffers and checks the browser PID afterward. It performs no repeat automatically.

Interpretation: a nonnegative return plus a new positive PID and a successful or `EPERM` signal-zero existence query would establish an out-of-process launch request from the browser. It would not by itself establish sandbox escape, because the service may intentionally authorize this Web App. A negative return establishes only that this exact call failed; it does not identify the policy stage unless the server-side error meaning is known. If the browser disappears before the result is captured, retain the last marker and use the operator's immediate on-screen observation; do not classify a memory warning as a successful launch.

The one device run returned `0x8094000F` from Sony's own launcher, which stored the same negative value in its process-ID slot (previously `-1`). App status returned `0` and its 12-byte response was `011700600001006001000000`; browser PID remained `145` and all owned state restored. No existence query ran because no positive PID was reported. [Launch capture](../captures/98444d0df63c414bb775062d60625a89.json). The current 14.00 client code checks null path/parameter and initialized-client state before its LNC request. Its add-process body does not directly contain `0x8094000F`; the captured RX image uses that immediate only in unrelated suspend-status paths. This narrows the error to a downstream request, reply, or transport path without naming its policy meaning. The existing path, complete built-in caller structure, and unchanged process slot justify parking this launch route until a new server-side discriminator appears.
