# Firmware 14.00 historical evidence triage

This audit reads `old-webkit-project` as historical evidence only. Its files were not changed. The results below are retained because the raw records say `firmware: "14.00"` and the contemporary handoff identifies a retail 14.00 console; the user has separately confirmed this console's version in Settings → System → System Information during the new project's runs. The old JSONL firmware field was supplied by the observer, and the exact browser binary and capture-time page bytes were not attested. These are leads to reproduce with the new collector, not imported primitives.

**Evidence labels:** The direct browser outcomes below are `observed-14.00` historical observations on the operator's console, subject to the trace provenance limit above. The exact browser build, source-level cause, native object layout, syscall identities, and kernel state remain `unknown`. Instrumentation bugs, stale page bytes, and heap state are alternative explanations for any single old trace; separate runs, the no-BigInt control, and the new independent probes distinguish them as far as the available evidence allows.

## Priority 1: a browser-process write with two independent oracles

The strongest old record is `muoofnk0-41ikmvdm` (`old-webkit-project/ps4-research-captures/muoofnk0-41ikmvdm.jsonl`, SHA-256 `48373bb3fa19133152f4fbd25ee937552a64c2b68357972ae5423dd2e1ed6472`). Its 61 events all carry firmware label `14.00`. The `owned-buffer-write` event reports a matched read of page-owned bytes, a write visible through an ordinary mirror, and restoration of the carrier and bytes. The later `owned-marker-object-write` event reports a second, distinct page-owned object's property changed through the memory view, observed both in JavaScript and via a memory read, then restored through both paths. All six relevant result flags were true with `error: null`. A fresh archive search found [14 separate 14.00 proof records](LEGACY_14_WRITE_RUNS.md) with those same six flags true, spanning September 30 and October 15; this is a count of matching records, not an attempt success rate. A separate 14.00 run, `muon9nvn-tolzp5xl` (SHA-256 `766362316307d76e16dd1469f7e97354c8d3582461ddc3fcb966cd2be56cb050`), also reports the owned-buffer write and restoration. Earlier 14.00 runs `muom38v3-xc53886j` and `muomhpcj-mgprz76i` report a known-byte read and restore; their file hashes are `688416e4c62b0f74018a9e72ad66101dc86f5b1ee0b4f3312eccaeffc5140978` and `9c75b9a1bdcf8c3cb44369de6e123c2767ded4b66e1507fbfe242c3cb73f45bf`.

This is evidence of a controlled **browser-process** effect on owned objects in the old observer. The old carrier used large allocations and relaxed header checks. We will not copy that carrier, object-layout constants, unvalidated earlier-firmware offsets, syscall labels, or kernel claims into the new project. The gadget locations that passed actual 14.00 byte checks are a narrow exception, subject to fresh live validation; see [the gadget decision](VALIDATED_GADGETS_14.md). A new native-memory claim requires a fresh, hash-pinned 14.00 run with a known-byte read, a distinct owned-object write, two independent oracles, and restoration.

## Priority 2: a browser-to-native call bridge was reached on 14.00

The old 14.00 `candidate-number20-call` proof in `muoxvgv8-a9ote9ig` (SHA-256 `08c2b03df33cb4468a10269b89b3a3a48607de9f0812f6a8b13bb5a80e0e3b32`) recorded `callReturned: true`, result `87`, a zero high return half, and restoration of the function slot, pivot cell, and memory carrier. A reload repeat, `muoxx762-c6lwxajs` (SHA-256 `e5708fca1b1d69a191d89c9b073bd12e898d11e390d269f40b6f820d3e6d3b64`), returned the same value. The handoff records a reboot before `muoyheng-0ofhi47h` (SHA-256 `49555608dddeb780ed524dab5c27b5ca4af26eb2c7afeffd507b3b15376e478c`), whose direct proof returned `63` with the same restoration flags. Later 14.00 `muoz215j-qqa5q0bz` (SHA-256 `f9b51598346bce146683b949a0d257278cf94e51678e8aa793ce96b84339b6e8`) recorded a socket-shaped open, option read into an owned buffer (`value: 1`, `length: 4`), and close, each with restored browser pointers. These are useful evidence that a native-call bridge and controlled user-buffer copyout were achieved in that observer. They do not prove a kernel bug or kernel memory access.

The old call preflight explicitly used gadget locations labelled `sourceFirmware: "13.00"`. The console nevertheless matched their bytes on 14.00 and executed a subset in the native-call pivot. Those checked locations can be used as candidates after re-reading their bytes at the current-process base. The old carrier, object layout, absolute addresses, and imported symbol assumptions are still excluded. An independent call bridge must validate its object and buffer addresses from the live 14.00 process.

The old observer source makes the execution mechanism explicit: it temporarily writes a candidate gadget address into a browser native-function slot, changes a pivot object's cell header, invokes `Math.expm1` on that object, and reads the native return from an owned frame before restoring both pointers. The three raw 14.00 return captures above are therefore strong evidence of **limited browser-process code-reuse execution** through a ROP pivot. They do not show injected or arbitrary payload execution. The exact page bytes served for those historical runs were not attested. The 14.00-checked gadget locations are reusable candidates, while the implementation is historical; the new project's WebKit-code-execution stage remains open until it independently reproduces an execution path from fresh 14.00 evidence.

## Priority 3: isolated large History clone anomaly

This is the best entry point for an independent test because it does not require the old carrier. Raw 14.00 `serialization-proof` event in `muopxp5b-3pbv05uh` (SHA-256 `f0a55e917ad3bdfb11d20abe70abf5faf02e70abc63090910b52e38dfed8ab42`) recorded a 65,536-element input array with a repeated object, followed by a 327,681-element `history.state` output with broken aliasing and a successful known-byte read/restore. More useful are the isolated `fw14-alias-control` captures: `muoq5a48-eqs2u5hq` (SHA-256 `79b3f77017b72d7c6681962db519487cbc1f5fe1fafa5d807f0fd1508a3e2bc`) and `muoq6cki-qxe4h2bo` (SHA-256 `0c8e2a29ef8456293a5fc21d5f81182e48d14a73d21d77d6bf79d32131c12ab1`). They used the large graph without carrier setup or native memory access and again returned length 327,681 with broken aliasing. Another 14.00 attempt, `muoq3lno-0wnekxd6`, threw `Unable to deserialize data` instead, so the large outcome is intermittent. In 14.00 reduction run `muoqbqni-5j4bcyi8` (SHA-256 `aab55521c4385614f4944943cab5bbb8fc2a326934390d16f307983134c4df40`), a matched large graph **without BigInt** preserved length 65,536 and aliasing.

The new project's [minimal clone finding](CLONE_INTEGRITY_FINDING.md) already reproduces a small BigInt reference substitution on the Settings-confirmed 14.00 console. The missing measurement is whether the large History shape, without old heap grooming, reproduces under the new hash-pinned collector. We will test that directly. The new test graph uses only values and sizes from the old runs performed on 14.00; it contains no native address, layout offset, or payload code.

## Deferred test and decision gates

The concise [console runbook](MORNING_HISTORY_RUN.md) gives the exact run order and outcome interpretation.

1. On a freshly loaded 14.00 research page, run [`clone_history_large_control_v1.json`](../probes/clone_history_large_control_v1.json) first. It checks a small ordinary History clone and the 65,536-element no-BigInt graph. Both should return `pass`, with output lengths 3 and 65,536 and preserved aliasing. A control error, warning, or missing result stops the comparison.
2. On a newly refreshed and connected page, run [`clone_history_large_bigint_v1.json`](../probes/clone_history_large_bigint_v1.json). It repeats the same small **number** control before the large BigInt graph, matching the old 14.00 control sequence without priming the page with another BigInt clone. The large case records output length, aliasing, slot type/value, and the tail control. `fail` here means a captured clone-integrity violation, while `error` records an exception and its phase. A memory warning without a saved result is a separate outcome, using the `bigint_large_ready` and `bigint_large_loaded` markers to locate the last completed phase.
3. If the large case returns length 327,681 or a repeatable phase-specific deserialization error with the large control passing, reduce the 14.00 graph in the new harness and seek a deterministic boundary. Rebuild a native-access experiment only after this independent reproduction, with run-local layout validation and an owned-object write/restore oracle. After that, re-derive a native-call bridge using only live 14.00 code bytes. If the large case behaves normally, retain the small confirmed clone defect and stop spending hardware runs on the old carrier shape.

The first fresh 14.00 comparison ran on October 19, 2026; see [the run record](HISTORY_14_RUNS.md). For later tests, inspect `python -m fw14lab.control sessions`, then enqueue each manifest with `python -m fw14lab.control enqueue-probe --session SESSION_ID --manifest probes/FILE.json`. Save command IDs, marker records, version-3 captures, source/manifest hashes, and any on-screen warning. Do not infer a crash solely from a missing result.

Prepared source SHA-256 values are `5674a6c9f38d1b5af65fdedcee35d08d32db204167eff12a79a759f11b6fe05b` for the control and `7d38089ef2aadf2ff9b9bc637f27e92cc3055a864873402310678bd4b29c3521` for the BigInt case. Their canonical manifest SHA-256 values are `e7a00c7fd3674e1a24908b1c4b7151d87021b4d6312b3f078d93bbea0c20ba2a` and `ce68fcce099977a3eedfc1d1c992435a5fd4ba8817f3f085d743da0a965957fd`, respectively. The version-3 captures record the bytes actually queued.

## Excluded material

- Unvalidated 13.52-and-earlier firmware tables, offsets, native object layouts, gadgets, and kernel exploit claims. The exception is gadget locations whose full instruction bytes matched in 14.00 device captures and will be rechecked live before use.
- The old initial `muolueq3-mdxq5nyv` addrof claim: its identity result was forced, so it was not a valid read proof.
- Old syscall sweeps, AIO/network grooming, and candidate kernel base: the 14.00 audit found no discriminating kernel memory effect, and syscall returns alone cannot establish a kernel vulnerability.
- The current project's canvas warning loop: it is a separate lead, and the user requested moving away from that path.

The old `fw14_observe.html` currently hashes to `a052455ee9f7b9657820e77b691534b2e16ab9cea50c3b221515789121e97b4c`. That is a hash of the file *now*, not proof that these exact bytes ran in any old capture; none of its implementation has been imported here.
