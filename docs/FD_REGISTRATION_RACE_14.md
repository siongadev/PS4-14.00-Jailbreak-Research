# Firmware 14.00 fd-registration race decision plan

The 2026-10-25 [write-side stress record](FD_REUSE_WRITE_STRESS_14.md) adds 1,664 captured close/reuse attempts across three native timing chains. None produced the old-source stale-note oracle. One later batch stopped after its start marker and has no result; browser status is pending observation.

Updated 2026-10-20. The upstream [FreeBSD fix](https://github.com/freebsd/freebsd-src/commit/8f3227f527567aef53da845ab78da8e16d9051c1) identifies a narrow interval: `kqueue_register` obtains a referenced file description with `fget()`, then locks the queue, then adds an fd-backed knote. A concurrent close can remove an existing note before the new note exists; if the numeric descriptor changes before registration, the old referenced file and new numeric descriptor may disagree. The fix adds a post-lock mapping check. **Sony firmware 14.00 kernel equivalence is unverified.** This file is an experiment design, not an exploit claim.

## Confirmed prerequisites on the current console

The browser page has reversible native calls with current-process wrapper and gadget checks. A separate worker has made a native call from its own plan, and two timestamped runs overlapped page and worker native calls. Two worker `kevent` waits were woken by the page with matching owned events. The [socket readiness control](../captures/00ff1166c66d409ea43b4db354905a5e.json) verified `EVFILT_READ` on an owned Unix stream socketpair. The [alias-close control](../captures/4db9593bb54545b6be985c8bd4bed098.json) verified that closing watched fd `10` removes its note while duplicate fd `12` keeps the original socket alive. The [sequential reuse control](../captures/f3d08853aef14a2b9a77448bf60fd0a0.json) verified that a new socketpair can reuse numeric fd `10`; neither old nor replacement source produced an event until its own descriptor was explicitly registered. Every reported descriptor was closed and owned bytes restored.

The earlier project's actual **14.00** worker registration/close/reuse attempt returned no event from either source (local prior-work archive: `old-webkit-project/KERNEL_PATH_AUDIT.md`, not included here). Its JavaScript progress ordering did not prove that close fell between `fget()` and queue locking. Its `dup2` controls returned `EPERM`, including an unwatched self-call, so this plan uses close plus a separately opened replacement and does not depend on `dup2`.

## Scheduling gate

The current page's [capability capture](../captures/2f5903af557c482e8c3caf46de320f2b.json) reports no `SharedArrayBuffer` and no cross-origin isolation. A second [transport capture](../captures/ef56231f49ef48eb808b6be53c258e95.json) establishes the more basic blocker: the PS4 loads this page over LAN **HTTP** and reports `isSecureContext=false`. [W3C Secure Contexts](https://www.w3.org/TR/secure-contexts/) does not classify an ordinary LAN HTTP origin as potentially trustworthy. `Atomics.wait` exists, but without shared memory it cannot coordinate the page and worker.

Cross-origin isolation headers alone cannot remove the measured insecure-context blocker. An isolated LAN HTTP route was considered and dropped; it would add a new page surface without enabling the shared-memory gate under the standard secure-context model. Keep the prepared [page/worker atomic barrier control](../probes/thread_shared_barrier_v1.js) for an authenticated HTTPS or otherwise trustworthy origin, if one becomes practical. For this LAN setup, prioritize a separately validated native rendezvous: a worker can wait in one native event-queue call and continue to a second native registration call without returning to JavaScript, while the page triggers the wake and closes/reopens the owned descriptor. First validate a two-call worker chain with benign calls and full restoration. This removes the previously measured worker-message delay, although it still cannot directly observe the internal `fget()`-to-lock interval. Repeating the previous message-only schedule at high volume would not improve interpretation.

The first continuation control [passed twice on 14.00](SANDBOX_WORKER_PATH_14.md): the worker stored a matching user-event wait result and then called the byte-checked number-20 wrapper **without returning to worker JavaScript**. Both passes returned the page's PID, intact event and guard, and full restoration. This establishes the native sequence and removes the earlier worker-message delay. It does not establish fd registration or a kernel race.

The second continuation control also [passed twice](SANDBOX_WORKER_PATH_14.md): after the same wake, the worker's second number-363 call registered a held socket read fd. A page-side write then produced one matching readiness event. This confirms the intended worker call shape and source-specific oracle without a close. The next bounded comparison can place a page-side close/reopen immediately after the wake, while recording both old and replacement sources. A normal result will remain inconclusive about the narrow kernel interval.

The first [close/reuse comparison](../captures/b58ba9361e4545ddaa3a8b0c2f752fe4.json) missed that scheduling gate: the page began its close after the worker had returned. Both source reads were empty and all cleanup passed, but this is not a test of the upstream interval. The next scheduling change must shorten the page's trigger-to-close gap before another comparison is interpretable.

A byte-checked page-side [three-call control](../captures/d4e3d8386efa429eb8bd0f192bc917ba.json) then passed. It allowed wake, close, and replacement open to run in one native chain. Three [revised comparison captures](SANDBOX_WORKER_PATH_14.md) produced one replacement-only event and two worker registration returns of `-1` with no source event. All had exact numeric reuse and full cleanup. The different results show that page/worker ordering varies, but neither result is the old-source stale-note oracle. Millisecond page/worker timestamps do not prove an internal `fget()`-to-lock overlap.

A four-call control also passed. Adding one `getpid` between wake and close produced two more completed comparisons with worker add `-1` and no source event. Later, an extended worker chain captured its immediate errno. Across two one-delay runs and two two-delay runs, the outcomes were `EBADF`/no source event twice and success/replacement-only event twice, with exact numeric reuse and cleanup in each. [Capture details](SANDBOX_WORKER_PATH_14.md). `EBADF` means the failed registration did not establish an old-source watch; it does not reveal whether the kernel has the upstream post-lock mapping check. The two-delay page control passed, but the extra `getpid` did not reliably shift the result. No comparison produced an old-source event.

These comparisons establish an error-code readback and ordinary scheduling alternatives, not Sony 14.00 kernel equivalence. The upstream `fget()`-to-lock interval remains unobserved. Another tiny page-side delay or an unbounded retry would have weak evidentiary value. Resume this candidate only if a distinct, validated mechanism can hold registration within that interval or another discriminator becomes available; otherwise investigate a different reachable 14.00 boundary interface.

Even a native wake controls userland entry time, not the internal `fget()`-to-lock interval. Before any fd-race run, calibrate one worker `EV_ADD` and one page close/reopen on owned descriptors, with direct, minimally logged timestamps and complete restoration. Only then run a small, bounded comparison. No unbounded spray or unattended repeated crash loop is part of this plan.

## One discriminating attempt

Open one queue and an old socketpair. Duplicate its read fd, retain both the old writer and duplicate, and verify the duplicate can still identify the old source. Have the worker attempt one fd-backed `EV_ADD` for the old read number while the page closes that number and opens one replacement socketpair. Require the replacement read endpoint to reuse the exact numeric fd. The worker's change buffer and page's call plans must be independent owned allocations, with wrapper bytes checked before calls. Record the worker return, both source writes, each zero-timeout queue read, output guards, descriptor closes, pointer restoration, and timing markers. A fresh sequential control and a repeated anomalous result are required before attribution.

| Outcome | Interpretation |
| --- | --- |
| Neither old nor replacement source signals | Normal close removal or missed kernel interval; this is the old 14.00 result and does not rule out the upstream race. |
| Only the replacement source signals after an explicitly registered replacement | Normal control behavior; not a stale note. |
| Old source signals through the old watched number after close/reuse, without re-registration | A candidate stale-note mismatch that differs from the sequential control; repeat on a fresh page, verify the event fields and cleanup, and seek an independent effect. It does not by itself show escape or kernel memory access. |
| Replacement source signals without its own registration | A separate unexpected association; verify numeric reuse and exclude an accidentally retained or newly installed watch. |
| Worker returns `EBADF`, `EEXIST`, or another error | Capture immediate errno and ordering; the return alone does not identify the kernel implementation. |
| Warning, refresh, or missing result | Capture preflight markers and last acknowledged call. A stale poll can also mean Rest Mode while the operator sleeps; it is not a crash signature by itself. |

A sandbox escape requires a later, independent authority readback: changed credentials, access to a previously denied protected resource, or a demonstrated out-of-process/kernel effect. Event behavior alone addresses the lifetime hypothesis. If the timing gate cannot be established or a bounded attempt only reproduces the prior no-event result, move to another candidate rather than labeling this one confirmed or disproven.
